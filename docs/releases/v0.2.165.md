# v0.2.165

发布时间：2026-10-28。三个现场修复 + owner 角色。

> ⚠️ **本版必须手动安装一次**：修复「自动更新失败」的代码在 v0.2.165 里，但你现在运行的 v0.2.162/0.2.164 没有那段逻辑，它仍会走旧的失败路径。装完 v0.2.165 之后，后续版本才能恢复自动更新。

## 1. 报告表格不再被分段切碎（#112 fix(im)）

**卡片通道一直是好的**，坏的是推送前的分段。

`splitForPush` 在单换行处切分，而表格行之间就是单换行 → 一张表被劈成两半，前后都不成表（表头错位、满屏竖线）。分段前缀 `【1/3】` 紧贴表头行时也会破坏表格首块。

- 分块改为**按块贪心装箱**（段落/标题/表格各自成块，表格永远整块）
- **超长表按行切分且每段重复表头 + 分隔行**——后续段落不再是「无表头的竖线墙」
- 分段前缀后按需补空行；标题不 stranded（保留既有契约）

实测 120 行表格的日报：修复前 4 段、末段无表头；修复后 3 段、每段都带表头。

## 2. 多 profile 更新失败 ENOENT（#112 fix(updater)）

```
ENOENT: no such file or directory, rename
  '…\pi-virtual-employee-updater\pending\temp-…0.2.164-x64.exe'
  -> '…\pending\…0.2.164-x64.exe'
```

`app-update.yml` 的 `updaterCacheDirName` 是打包时的**静态值**，不随 profile 变——所有 profile 共用同一个 `%LOCALAPPDATA%\pi-virtual-employee-updater\pending\`。两个实例同时下载同一版本时，先完成的一方把 temp 文件 rename 走，另一方报 ENOENT；而 electron-updater 内部对 rename 只重试 `EBUSY`，`ENOENT` 直接放弃。

- `setupAutoUpdater` 按 profile **隔离缓存目录**（`pi-virtual-employee-updater-<profile>`），default 保持原路径以免孤立刻在途下载
- `ENOENT` rename 竞态进入既有退避梯（30s / 2min / 10min）

> 这是「双 profile 共享机器级资源」的第三次同型事故（前两次：钉钉消息竞争、任务删除只删一侧）。

## 3. owner 角色（#113 feat(rbac)）

角色扩为 `viewer < operator < admin < owner`。

**解决的实际问题**：自主任务/定时任务的变更被限制在来源会话（防数据越权，正确），但这条规则把**部署所有者本人**也挡在外面——「我是 owner，还要跑到另一个会话去改」。租户隔离约束的是不同人/群之间，不应约束整个部署的所有者。

- `owner` = admin 全部权限 **+ 可跨会话变更任务**
- `admin` 仍**不能**跨会话变更（多 admin 部署下租户隔离依然成立）
- 授予方式：`security.ownerStaffIds` 列表，或设置页人员角色选「owner」
- `defaultRole` 禁止设为 owner（它作用于所有未知发送者，等于把全世界变 owner）

两个实现坑：`isAdmin` 放宽为 `owner ⊇ admin`（否则授予 owner 会**反而失去** admin 能力）；`normalizeSecurity` 必须显式列出 `ownerStaffIds`（白名单式重建会静默丢弃新字段）。

`rbac-gate` 守护区已 ACK 重算 manifest。
