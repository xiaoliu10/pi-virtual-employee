# v0.2.224

## English

### Question→answer handoff closes the loop — even after the keep-alive window closes

v0.2.223 taught workers to keep receiving their conversation for two minutes past two hours (the keep-alive window). This release closes the remaining gap with a **state-based** counterpart: when a finished worker's settled output ends with an input request — 「发给我（6位数字）」「请提供订单号」 — a bare token sent at *any* age is recognized as the **answer** to that ask and routed into the asking worker's session, instead of falling to a foreground conversation that never saw the question.

Why the foreground can never answer these: worker deliveries are push-only — the worker's question never entered the chat history the foreground turn rehydrates. A naked 「847159」 arriving there gets 「这串数字我这边没有对应的上下文」 at best, a fabricated action at worst (the v0.2.223 incident). The asking session, by contrast, holds its own plan and knows exactly what the number is for.

The ask detector (`looksLikeInputRequest`) is deliberately narrow: only the last ~160 characters are examined (the ask is by definition the last thing the worker said), only curated phrasings match (「发给我」「请提供」「请输入」 with look-behind guards against quoted UI prompts like 「登录页一直提示请输入验证码」), and every uncertain shape fails open to the foreground. Captures apply to `done` workers only — cancelled runs (the user pulled the work back; the foreground rerun owns the payloads) and interrupted runs (the contract is 「重新执行」) keep the foreground path.

Composed with v0.2.223's keep-alive window, the routing matrix is now: hot window → the worker receives everything non-task; cold window → a pending ask still captures its answer, everything else resolves in the foreground.

Verification: 140 test suites pass (worker-service suite grew to 50 tests, including a 26-hour-old ask capturing its answer and error-status rows refusing capture), both typecheck projects clean, asar gates pass on both platforms.

## 中文

### 问→答断链闭环——保活窗口关了之后也不断

v0.2.223 让 worker 在收尾后的两小时窗口内继续拥有对话。本版补上**状态维**的另一半：当已收尾 worker 的落库输出以输入请求结尾——「发给我（6位数字）」「请提供订单号」——**无论过了多久**，收到的裸 token 都会被识别为该请求的**答案**，路由进提问的 worker 会话，而不是落到一个从没见过问题的前台。

前台永远答不了这类消息：worker 的投递是 push-only——它的提问从未进入前台回合读取的聊天历史。裸「847159」到那里，最好被回「这串数字我这边没有对应的上下文」，最坏被编造成一个动作（v0.2.223 事故本体）。而提问会话自己持有计划，知道这个数字是干什么用的。

问句探测器（`looksLikeInputRequest`）刻意收窄：只看最后 ~160 字符（提问按定义是 worker 说的最后一句话）、只匹配精选句式（「发给我」「请提供」「请输入」并对转述 UI 提示的形态加 look-behind 排除，如「登录页一直提示请输入验证码」），一切拿不准的形态 fail-open 回前台。捕获仅作用于 `done` 状态——已取消（用户拉回前台，载荷归前台 rerun）与已中断（契约是「重新执行」）维持前台路径。

与 v0.2.223 的保活窗口合成后，路由矩阵为：热窗内 → worker 收下一切非任务消息；超窗后 → 挂起的提问仍会捕获自己的答案，其余在前台解析。

验证：140 套件全过（worker-service 增至 50 测试，含 26 小时前的提问捕获答案、error-status 行拒绝捕获）、双 typecheck 零错、双平台 asar 闸门通过。
