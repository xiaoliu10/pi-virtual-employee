# v0.2.225

## English

### Credentials are masked in place instead of destroying the whole message

Until now the outbound gate had one blunt answer to a credential: **withhold everything**. A scheduled report that quoted a share link with `?access_token=…`, or a log line that mentioned `password: 123456`, arrived as「这条回复含账号密码/密钥等敏感凭据，已按安全规定拦下，未发送明文。」— the report itself was thrown away even though its body carried no secret at all.

v0.2.225 replaces that with **masked delivery**: the credential-shaped value is replaced by `***` in place, the rest of the message is delivered verbatim, and the existing suffix notice (「检测到敏感凭据 N 处，已脱敏发送」) still tells the reader what happened. The contract that matters is unchanged — **no string that the previous gate withheld may now be delivered containing its secret in plaintext** — and anything the masker cannot prove safe still withholds the whole message, exactly as before.

Report and share links keep working, which is the whole point of the release:

- Gitee raw share links keep their owner/repo routing readable; only the credential parameters and any concrete secret in the branch/file path are masked (`…/raw/master/report.xlsx?access_token=***`).
- OSS/S3 presigned URLs are never rewritten: `OSSAccessKeyId`/`Expires`/`Signature`, `X-Amz-Algorithm`, `X-Amz-Credential`, `x-oss-process`, `response-content-disposition` … are all part of the signature, so the link is delivered byte-for-byte. Masking any of them would produce a dead link that looks alive.

The re-check also had to learn that a redacted marker is not a licence to ship whatever follows it. Separator-free glue (`…?access_token=***。密码First_123456`), nested URLs (`…?access_token=***https://example.com/Abc_123456`), userinfo carriers (`https://Abc_123456:x@host/…`), fragments (`…/r.md#First_123456`) and scheme-less `www.` tails all fail closed: the residue is inspected with the same value heuristic as a labelled credential, and anything that looks concrete removes the tail (matching the old gate's truncation) while pure CJK prose (`，请查收。`) and clean report links keep delivering.

Verification: the change went through **14 independent review rounds**, each one attacking the previous verdict; every finding either fixed with a regression pin or dispositioned with evidence. 140 test suites pass, both typecheck projects are clean, the immutable-kernel gate reports 16 guarded regions unchanged, and the dedicated fuzz corpus (79,396 constructed message shapes) reports **0 new leaks, 0 non-idempotent outputs, 0 new withholds** against the previous release.

## 中文

### 凭据就地打码，不再整条销毁消息

此前出站闸门对凭据只有一种粗暴答案：**整条拦下**。一份定时报告只要引用了带 `?access_token=…` 的分享链接，或一行日志里出现过 `password: 123456`，用户收到的就是「这条回复含账号密码/密钥等敏感凭据，已按安全规定拦下，未发送明文。」——报告本体一个秘密都没有，却照样被丢掉。

v0.2.225 改为**脱敏放行**：凭据形态的值就地替换成 `***`，消息其余部分逐字节投递，既有后缀提示（「检测到敏感凭据 N 处，已脱敏发送」）照常告诉读者发生了什么。真正重要的契约不变——**旧闸门会拦下的任何字符串，如今投递时也不得带有其秘密的明文**——打码器无法证明安全的内容，仍然整条拦下，与之前完全一致。

报告与分享链接照常可用，这正是本版的意义：

- Gitee raw 分享链接保留 owner/repo 路由可读；只有凭据参数与分支/文件路径中的具体秘密被打码（`…/raw/master/report.xlsx?access_token=***`）。
- OSS/S3 预签名 URL 绝不改写：`OSSAccessKeyId`/`Expires`/`Signature`、`X-Amz-Algorithm`、`X-Amz-Credential`、`x-oss-process`、`response-content-disposition` 都是签名的一部分，链接逐字节投递——改动其中任何一个只会制造一条「看起来还活着」的死链。

复检还必须学会一件事：**打码标记不是放行后续内容的通行证**。无分隔符粘连（`…?access_token=***。密码First_123456`）、嵌套 URL（`…?access_token=***https://example.com/Abc_123456`）、userinfo 载体（`https://Abc_123456:x@host/…`）、fragment（`…/r.md#First_123456`）以及无 scheme 的 `www.` 尾巴，一律 fail-closed：残留内容用与带标签凭据相同的取值启发式检查，任何具体值都会移除整段尾（与旧闸门截断行为一致），而纯中文正文（`，请查收。`）与干净的报告链接照常投递。

验证：本次改动经过 **14 轮独立复审**，每轮都在攻击上一轮结论；每条意见要么修复并补回归钉，要么附证据说明处置。140 套件全过、双 typecheck 零错、不可变内核闸门报告 16 个守护区未变；专用 fuzz 语料（79,396 条构造消息形态）相对上一版报告 **0 新增泄漏、0 非幂等输出、0 新增保守拦截**。
