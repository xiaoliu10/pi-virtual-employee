## 0.2.122

### 修复

- **开启「管理员完全访问」后，员工不再反复索要「确认」**（现场反馈：已开启完全访问，切换默认模型时员工仍回复「请回复确认，我再将默认模型切换为 step-5-preview」）。硬门控其实早已放行（`adminFullAccess` 在 `requireConfirmedAdmin` 短路确认要求），但 manage_settings / manage_computer / manage_capabilities 三个工具的**描述文案是静态的**，仍在教模型「写入需确认」「model 块有失联风险请谨慎核对」——模型于是礼貌地继续问。现三个工具描述按开关状态动态生成：开启时明确「写入仅需管理员身份，管理员明确指示即可直接执行，无需再索要确认」；关闭时保持原确认要求。这是「门控必须镜像到 prompt」规则的第三次应用（前两次：#29 幽灵工具、#33 kb 门控）。
- 复审处置（0H→1H 抓出后全修）：① 描述拼接处 `+ +` 一元加号把 action=list/get 整句说明变成字面 `NaN`（typecheck 盲区，测试补 NaN 哨兵）；② `manage_access set_full_access` 写配置后漏调 `onConfigChanged`——IM 内开启完全访问后同会话描述不刷新，硬门放行但 prompt 仍是旧文案（正是现场症状的残留路径）；③ 镜像补齐 settings 三处残留静态确认文案（参数描述 / list 运行时响应 / autonomousMining 行）；④ OFF 分支与原文逐字等价的 golden 断言 + ON 分支全文禁教导确认（唯一豁免：manage_work_items 提案的「确认创建」属业务协议非门控）。manage_process kill / manage_update install_now 的确认是独立实现（不走 requireConfirmedAdmin，完全访问不短路），描述如实保留——已在 PR 反驳复审 M2 并记录。
- 不可变护栏 re-pin ×2：`test-permissions.mjs` 镜像用例（含上述加固），`verify-immutable.mjs` 的 `MANIFEST_SHA256` 同步（刻意显眼 diff），IMMUTABLE_ACK 原因已记录。

### 说明

- `manage_access set_full_access value=on` 本身仍需一次「确认」——这是刻意的非对称门控（开启要难、关闭要易），不受完全访问状态影响。
