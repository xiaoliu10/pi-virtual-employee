# v0.2.190

**English**

### Long tasks no longer occupy the chat (Router/Worker P1, gray release)
- The field's biggest complaint — a 09:42 monitor job holding a conversation for 85 minutes while a 10:21 message queued for 30 — is an architecture problem: one chat turn carried both "conversation" and "long task execution".
- A message the planner judges task-shaped (**≥2 numbered steps AND a long-running verb** — deploy / scrape / batch / export / reconcile / build …) is now acknowledged and handed to a background work item. The chat stays responsive; progress and results push back to the same conversation.
- Triage is deliberately conservative. Simple questions, single-step commands, question-shaped text, and **every failure mode** (no plan, LLM unavailable, non-admin sender, dispatch error) stay inline — a triage failure can never swallow a message.
- `general.chatDispatch` is **OFF by default**; with it off, behaviour is unchanged byte for byte.
- Dispatched tasks jump the queue (`work_items.priority` 0 vs 100 for mined work), so "已转后台" cannot quietly mean "queued behind a mining window".

### Authoring a script no longer means fighting three layers of escaping
- VE had no write tool at all: creating a script meant inline `echo >` / `Set-Content` / `python -c`, stacking the JSON argument, the shell's quoting and the target language's syntax — failing repeatedly in ways unrelated to the user's task.
- New `write_text_file` takes the file body as an ordinary argument (UTF-8, no BOM), verifies by reading back, and writes **atomically** (temp file + rename) so a failed write cannot destroy a working script.
- Confined by the same whitelist as list/delete, plus a deny-list for the app's own databases and config; the workspace lives in its own root outside every profile.
- `run_script` (parameters via JSON file) completes the chain: no user data on any command line.

### Progress notes actually fire again (P0)
- The IM heartbeat read `agent.state.isStreaming`, which the durable kernel never sets — every tick returned silently, so a 20-minute turn produced zero progress notes despite `longTaskProgressMin=10`.
- The fix was written on 2026-11-03 but never merged to main. It now asks the kernel (`isConversationStreaming`).

### Plans are gated and readable
- A plan is pushed to chat only when the work is estimated at **≥30 minutes** — a task that finishes in a minute does not need a plan pushed at it.
- What IS pushed is a short human outline (goal / flow / ETA) instead of a mechanical numbered checklist; the full steps still go to the executing turn as context.

### Recovery: parked messages are re-driven
- A submission left in `placed` (queued behind a run the restart killed) used to wait out the recovery timeout and report "执行已暂停" for a message that never ran. Recovery now re-drives it with a durable `continue`.

### MCP: the guard test could not fail
- The test pinning "MCP tools are visible to the durable kernel" read `harness.registry`, a handle that does not exist — so its assertions never executed and the fix shipped behind a permanently green check.
- Repaired, plus a real stdio end-to-end chain (startup connect, late connect, RBAC execution).

### Update watchdog: profile identity survives a mangled launch
- A main process without `--profile` was recorded as the default profile, so the watchdog relaunched it bare — an instance with no identity, and every later snapshot inherited that empty entry.
- Identity is now recovered from a child's `--user-data-dir`, requiring **≥2 agreeing children** so an orphan cannot confer the wrong profile.

**中文**

### 长任务不再占死聊天（Router/Worker P1，灰度）
- 现场最大的抱怨——09:42 的监控任务占住会话 85 分钟、10:21 的消息排队 30 分钟——是架构问题：一个聊天回合同时承担「对话」与「长任务执行」。
- 规划判定为任务型（**≥2 编号步骤且含耗时动词**——部署/抓取/批量/导出/对账/构建…）的消息，现在先进回执、再交给后台工作项。前台继续可聊，进度与结果回投同一会话。
- 分诊刻意保守。简单问答、单步命令、提问形状、以及**任何失败**（无规划、模型不可用、非管理员、派发异常）一律留在前台——分诊失败绝不吞消息。
- `general.chatDispatch` **默认关闭**；关闭时行为逐字节不变。
- 转派的任务会插队（`work_items.priority` 0，挖掘任务 100），「已转后台」不会悄悄变成「排在挖掘窗口后面」。

### 写脚本不再和三层转义搏斗
- VE 此前根本没有写文件工具：创建脚本只能用内联 `echo >` / `Set-Content` / `python -c`，JSON 参数、shell 引号、目标语言语法三层叠加，反复以与用户任务无关的方式失败。
- 新增 `write_text_file`：文件内容作为普通参数（UTF-8 无 BOM）、写完读回校验、**原子写**（临时文件 + rename），失败不会毁掉可用的旧脚本。
- 受与 list/delete 相同的白名单约束，另加应用自身数据库与配置的黑名单；工作区位于所有 profile 之外的独立根目录。
- 配合 `run_script`（参数走 JSON 文件），整条链路命令行零用户数据。

### 进度汇报恢复推送（P0）
- IM 心跳读 `agent.state.isStreaming`，而 durable 内核从不设置该标志——每个 tick 静默早退，20 分钟的回合零进度，尽管 `longTaskProgressMin=10` 明明生效。
- 该修复 2026-11-03 就写好了，但从未合入 main。现在改为问内核（`isConversationStreaming`）。

### 规划加了时长门控、可读性提升
- 只有预计 **≥30 分钟** 的任务才把规划推到聊天——一分钟就完的任务不需要被推一份规划。
- 推的是简短人话大纲（目标 / 流程 / 预计耗时），而不是机械编号清单；完整步骤仍作为上下文交给执行回合。

### 恢复：已排队（placed）的消息会被重新驱动
- 排在「被重启杀掉的那次运行」之后的 submission，原来只能干等到恢复超时，并对一条从未执行的消息报「执行已暂停」。现在用 durable `continue` 重新驱动。

### MCP：那条守护测试根本不可能失败
- 用来钉住「MCP 工具对 durable 内核可见」的测试读 `harness.registry`——该句柄不存在，断言从未执行，修复在永远绿的勾选下发布。
- 已修复，并补了真实 stdio 端到端链路（启动期连接、迟到连接、RBAC 实际执行）。

### 更新 watchdog：参数被剥离时身份不丢
- 无 `--profile` 的主进程被记为 default profile，watchdog 于是裸启动它——一个没有身份的实例，且后续每次快照都继承这个空条目。
- 现在从子进程的 `--user-data-dir` 反推身份，要求 **≥2 个一致子进程**，防止孤儿子进程撞 PID 导致的身份错配。
