# v0.2.221

## English

### Auto-compaction actually works now — two upstream fixes backported

A day-long browser-automation worker hit the model's hard 200k-token context limit, and three "successful" compactions left the transcript *larger* than before (198,936 → 199,722 → 210,321 tokens), each taking ~80 seconds. The compaction machinery was running; the summarization request itself was broken.

Investigation against pi-desktop showed why desktop stopped having this problem: desktop does not implement compaction at all — it runs pi-coding-agent 1.5.0's `AgentSession`, which owns the whole lifecycle and inherits upstream fixes. VE vendors a 1.1.0 snapshot of the compaction primitives (to keep the installer under the asset-size cap) and drives them itself, so it never received two later upstream fixes:

- **Reasoning chains no longer go into the summarizer.** The vendored snapshot serialized `[Assistant thinking]: …`, feeding hundreds of turns of full model reasoning into the request that was supposed to *shrink* the context. Upstream omits thinking for exactly this reason: "including it can make the summarization request larger than the context it summarizes." Visible text, tool calls and tool results record what happened; thinking does not. A worker-shaped transcript now serializes to a small fraction of its own size.
- **Summaries use the model's own output limit.** The snapshot capped summary output at `0.8 × reserveTokens` = 13,107 tokens. On a reasoning model the thinking alone consumes that cap, so the summary came back truncated and was rejected — compaction could never succeed on precisely the transcripts that needed it most. Upstream removed this cap (#9512); the reserve argument is now unused, matching upstream.

### Conversation stickiness restored

The 30-minute window on follow-up injection into a finished worker (shipped in 0.2.220) is reverted: a conversation staying with the worker that did the work is the intended design, and with compaction fixed the transcript cannot snowball. 「结果呢」/「继续」 hours later still reach the original worker. New task requests and bare reference tokens (order numbers, codes) still route to a fresh worker or the foreground conversation instead of landing in an accumulated transcript, and the pre-turn budget gate bounds every turn regardless.

## 中文

### 自动压缩现在真的能压了——backport 两个上游修复

一个跑了整天的浏览器自动化 worker 撞上模型 20 万 token 硬上限，三次「压缩成功」后 transcript 反而**更大**（198,936 → 199,722 → 210,321 token），每次耗时约 80 秒。压缩机制在跑，坏的是摘要请求本身。

对照 pi-desktop 查明了 desktop 为什么不再犯这个病：**desktop 根本不自己实现压缩**——它跑 pi-coding-agent 1.5.0 的 `AgentSession`，整条生命周期由上游拥有，上游修复自动继承。VE 为把安装包压在资产体积上限内，vendored 了 1.1.0 快照并自己驱动，因此从未拿到上游后来的两个修复：

- **推理链不再进摘要器。** 旧快照会序列化 `[Assistant thinking]: …`，把几百回合的完整模型推理喂进那个本该**缩小**上下文的请求。上游省略 thinking 的理由正是本次事故：「including it can make the summarization request larger than the context it summarizes」（把它算进去会让摘要请求比它要摘要的上下文还大）。可见文本、工具调用、工具结果才记录发生了什么，思考不记录。worker 形状的 transcript 现在序列化后只占自身的一小部分。
- **摘要改用模型自身的输出上限。** 旧快照把摘要输出钳在 `0.8 × reserveTokens` = 13,107 token。推理模型光思考就吃满这个额度，摘要回来就是截断的、随即被拒绝——**恰恰在最需要压缩的超长 transcript 上压缩永远无法成功**。上游已移除该 cap（#9512），reserve 形参现为 unused，与上游一致。

### 恢复对话粘连

0.2.220 引入的「结束 worker 30 分钟注入窗口」已撤回：一个对话粘连到干活的那个 worker 本就是设计意图，且压缩修好后 transcript 不会再滚雪球。数小时后的「结果呢」「继续」照常到达原 worker。新任务请求与裸引用 token（单号、编码）仍走全新 worker 或前台会话、不落进累积账本，而入轮预算门对每个回合无条件兜底。
