# v0.2.199

## English

### The watchdog fired, nothing died

An autonomous task on the box spun for half an hour at ~18 LLM calls per minute. The progress watchdog saw the loop and fired every four seconds — and the loop kept running.

`runtime.abort()` called `conv.abort(context)`, dropping the options argument. pi-durable's `abortConversation` marks only **non-background** tasks by default, and autonomous/work-window runs hang off background nodes. Every soft-stop marked nothing. Abort "succeeded", the run survived, and only the LLM bill could tell.

A restart made it worse: `running` tasks flip back to `pending` and resume replays the same loop from its checkpoint.

- `conv.abort(context, { background: true })` — the abort now reaches what it aims at.

### Killed, then re-armed, then killed again

A soft-stopped window used to keep its NEXT_CHECK and re-arm itself: kill → re-arm → kill, forever.

- The engine now counts watchdog soft-stops per conversation in a 30-minute sliding window.
- Before a window schedules its follow-up, `WorkService` consults that count. One soft-stop demotes the window to "needs a human" instead of re-arming; a second one says so plainly and recommends cancelling or splitting rather than resuming again.
- A window that ran out of wall clock is exempt: its deferral is the documented long-task shape, not a spin.
- A window that closes normally clears the count — otherwise one transient loop would demote the item forever.

### A task that finished reported "execution paused"

The run completed its work — "登录成功" was already written — and died before its submission settled. Recovery found no answer record and pushed 「执行已暂停，请检查恢复状态。」 The real reply was sitting in the conversation's entries, unread.

- When the answer record is missing, the last real assistant message is read back instead of guessing. Synthetic delivery notices are skipped, so the model cannot learn to imitate its own fallback.

### The bot answered, then went quiet

The push ledger dedupes on an occurrence id, and recovery used `durable:<convId>:answer` — **identical for every turn of the same conversation**. The second message's reply hit the first message's ledger row and was dropped as "already delivered". The user saw one answer and then silence, and the log said the delivery had succeeded.

- The occurrence id now includes the per-run submission id.

### Three @-mentions, zero words back

Worker windows killed by a restart were flipped to "needs a human" **silently**: three dispatches succeeded (`fired=true`), and not one reply came back.

- Recovery now returns the affected items and pushes an honest notice per origin conversation: the task was interrupted, its progress is kept, and a human must decide.

### "Settle verification" had no end

Five tasks spent ten minutes each writing and running new check scripts (`chk_bastion_session.py` → run → "verify once more" → `chk_envs.py` → run → …). Every step was a legitimate tool call with fresh content, so no time-window watchdog can see it.

- The immutable discipline block now bounds it: **at most two verification rounds per goal**, then a final answer either way. Writing a fresh temporary script in place of reporting is called out as spinning, not progress. Saying "could not verify" is more valuable than verifying forever.

### Workers cannot grow the task lists

Merged from #165: a worker window may not call `create_scheduled_task`, and `manage_work_items` refuses `mine`/`confirm`/resident derivation inside a worker. Router/Worker is a one-shot async call — it derives at most one-off follow-ups and never pollutes the global task lists.

### Smaller

- The "thinking" reaction no longer fails silently: a missing field, a thrown error, or a non-2xx response is logged with the reason DingTalk returns.
- Fixed a self-inflicted test hang (a never-resolving gate wedged `whenIdle()` and timed out the whole suite twice).

### Quality

122 test suites green; both tsconfigs clean; immutable guarded regions unchanged (the discipline change is a pure addition and was acknowledged with reason). Nine mutations killed: gate removal, escalation copy disabled, interrupted push removed, recovery not returning victims, abort losing its options, the gate querying the wrong key, no reset on a normal close, reset on demotion, and a constant occurrence id.

## 中文

### 看门狗开火了，什么都没死

盒子上一个自主任务以每分钟约 18 次模型调用的速度空转半小时。进度看门狗看见了，每四秒开一次火——循环照跑。

`runtime.abort()` 调的是 `conv.abort(context)`，options 参数被丢了。pi-durable 的 `abortConversation` 默认只标记 **non-background** 任务，而自主任务/work 窗口的 run 全挂在 background 节点下。于是每次 soft-stop 什么都没标记：abort「成功」、run 照活，只有账单能看出异常。

重启只会更糟：`running` 翻回 `pending`，resume 从 checkpoint 重放同一个循环。

- 改为 `conv.abort(context, { background: true })`——abort 现在能打到它瞄的东西。

### 掐了又顺延，顺延了再掐

被软停的窗口原来会保留 NEXT_CHECK 自我顺延：杀 → 起 → 杀，永不停止。

- 引擎按会话在 30 分钟滑动窗内统计看门狗软停次数。
- 窗口顺延前 `WorkService` 先查这个计数：一次软停就把窗口降级为「需要人工」而不是自我顺延；第二次直接说明并建议取消或拆小，而不是再恢复一次。
- 窗口时间上限顺延被豁免——那是文档写明的长任务形态，不是空转。
- 正常收尾的窗口清零计数——否则一次偶发循环会让任务永远被降级。

### 任务明明完成了，却报「执行已暂停」

run 干完了活（「登录成功」都写出来了），死在 submission settle 之前。恢复扫描找不到答复记录，于是推送「执行已暂停，请检查恢复状态。」真实答复就躺在会话 entries 里，没人读。

- 答复记录缺失时，改为读回最后一条真实的 assistant 消息，而不是猜。合成投递通知会被跳过，否则模型会学着模仿自己的兜底文案。

### 机器人答了一句，然后就没声了

推送台账按 occurrence id 去重，而恢复用的是 `durable:<convId>:answer`——**同一会话每一轮都一模一样**。第二条消息的答复命中第一条的台账行，被当成「已投递」丢弃。用户看到答了一次然后沉默，日志却说投递成功。

- occurrence id 现在拼上每次运行唯一的 submission id。

### @ 了三次，一个字都没回

被重启打断的 worker 窗口被静默翻成「需要人工」：三次派发全部成功（`fired=true`），一条回复都没有。

- 恢复现在会返回受影响的条目，并逐条向来源会话推送如实通知：任务被中断、进度已保留、需要人工决定。

### 「收尾验证」没有终点

五个任务各自花了十分钟写新检查脚本、跑、再「核实一遍」、再写一个（`chk_bastion_session.py` → 跑 → `chk_envs.py` → 跑 → …）。每一步都是内容全新的合法工具调用，任何基于时间窗口的看门狗都看不见。

- 不可变纪律块现在给它设了边界：**同一目标最多两轮验证**，之后无论结论如何都必须给出最终答复。明确点出「再写一个新的临时脚本代替汇报」是伪装成进展的空转。说「未能验证」比无限验证更有价值。

### Worker 不能给任务列表添油

合并自 #165：worker 窗口不得调用 `create_scheduled_task`，`manage_work_items` 在 worker 内拒绝 `mine`/`confirm`/常驻派生。Router/Worker 是一次性异步调用——最多派生一次性后续任务，绝不污染全局任务列表。

### 其他

- 「思考中」表情不再静默失败：缺字段、抛异常、非 2xx 都会连同钉钉返回的原因一起记下来。
- 修掉一个自己引入的测试挂死（永不 resolve 的 gate 卡住 `whenIdle()`，让整套测试两次超时）。

### 质量

122 个测试套件全绿；两个 tsconfig 干净；不可变守护区未变（纪律改动为纯增量并已带理由登记）。九个变异全部被杀：闸门移除、升级文案禁用、中断推送移除、恢复不返回条目、abort 丢参数、闸门查错 key、正常收尾不清零、降级时误清零、occurrence id 退回常量。
