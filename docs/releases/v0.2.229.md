# v0.2.229

## English

### An unrelated request typed into a busy single chat now gets its own worker

Field 2026-11-12 (`dt:manager5792`): a 5-hour SLS reconciliation worker occupied Nova's single chat. The user answered the worker's question with 「要」, then sent an unrelated 「明天天气」. The logs show what happened to the weather request: it was **steered into the SLS worker** — a session carrying ~157k tokens of browser-forensics context, compressed 7 times — which then interrupted its own task to run `_weather_fetch.py` and answer the weather before returning to the SLS work. No second worker was ever spawned; every follow-up, related or not, funnels into the one running worker.

v0.2.229 adds a bounded side-pass classifier to that decision point. When a follow-up arrives for a live worker, `engine.classifyWorkerFollowUp()` judges — in a side call capped at 60s, counted as watchdog liveness — whether the message **continues** the run (CONT) or is a **new task** (NEW):

| verdict | behavior |
| --- | --- |
| `CONT` | steered into the running worker, as before |
| `NEW` | `inject()` declines; the message returns to triage, which dispatches a **parallel worker** with clean context |
| classifier failure / timeout / ambiguity | **fail-safe CONT** — never spawns a second worker that would race the same target (the flood-loop lesson) |

Bare context tokens (verifying codes) and cancel phrases skip the classifier entirely: a verification code is an answer, and 「取消」 must never wait for a classification round-trip.

### Dispatch decisions moved out of the serial chat queue

The queue's only reason to exist was the kernel's refusal to run concurrent `prompt()` calls on one session — yet the *routing* decisions (draining check, roster/RBAC, foreground escape, planner bypass, worker dispatch) were made **inside** it. A hung inline turn therefore blocked the next sentence from even being triaged. `IMManager.handle()` now runs all routing decisions before queue admission; only the inline execution body (watchdog + `engine.send`) still serializes. A new task now dispatches in ~5 ms while an inline turn hangs; ordinary questions keep FIFO order.

### Per-profile updater cache isolation that actually isolates

The field incident behind this fix: all three box profiles shared **one** updater pending directory and deleted each other's downloads mid-flight (family-wide ENOENT), twice, which tripped the update circuit breaker. The root cause was that the `isolateUpdaterCache` guard called `setUpdaterCacheDir()` — an API that **does not exist** in electron-updater 6.8.9 — so every profile silently returned without isolating anything. The fix pre-seeds `autoUpdater.downloadedUpdateHelper` with an isolated directory, which the real 6.x code path honors. The new rule: isolation either **HAPPENS** (INFO with the directory name) or **SAYS SO** (WARN with the reason) — a silent return is exactly the bug shape this fixes.

### User follow-ups refresh the progress-push budget

Same 5-hour run, second defect: push #20 landed at 20:09 and every later pump beat was dropped by `progress push cap (20) reached` — permanently. The cap is anti-spam for an absent audience; a user actively steering the run is by definition present. An accepted follow-up now resets the run's budget in place (`progress budget reset by user follow-up (was N/M)`), without ending the run — the already-capped run recovers on the user's next message, no task restart needed. Only the cap counter resets: the degraded-LLM backoff is relay-health and keeps its own state. And a suppressed budget is now **zero-cost**: the cap check moved before the side-LLM summarize, so a capped tick no longer burns a bounded model call just to log and drop the note (the box had been doing this every 10 minutes for hours).

Gates on the merged code: **145 test suites pass**, both typecheck projects clean, immutable-kernel gate reports 16 guarded regions unchanged.

Field-verification boundary: verified against real Agent loops and the real updater module in tests; the deployment box upgrades through its own channel.

## 中文

### 忙碌单聊里发来的无关请求，现在有自己的 worker

现场 2026-11-12（`dt:manager5792`）：一个跑了 5 小时的 SLS 对账 worker 占着 Nova 的单聊。用户先回了句「要」，又发了句不相干的「明天天气」。日志记录了天气请求的下场：它被 **steer 进了 SLS worker**——一个背着 ~157k tokens 浏览器取证上下文、压缩过 7 次的会话——然后这个 worker 打断自己的任务，跑 `_weather_fetch.py` 回答了天气，再回头继续 SLS 的活。自始至终没有开出第二个 worker；所有追加消息无论相关与否，全都灌进同一个运行中的 worker。

v0.2.229 给这个决策点加了有界旁路分类器。follow-up 到达 live worker 时，`engine.classifyWorkerFollowUp()` 在一次**上限 60 秒**的旁路调用里（计入看门狗活性）判断这条消息是**继续**当前任务（CONT）还是**新任务**（NEW）：

| 判定 | 行为 |
| --- | --- |
| `CONT` | 照旧 steer 进运行中的 worker |
| `NEW` | `inject()` 拒收，消息回到分诊，派发**并行 worker**（干净上下文） |
| 分类失败 / 超时 / 歧义 | **fail-safe CONT**——绝不开出第二个 worker 去抢同一目标（刷调用事故的教训） |

裸上下文 token（验证码）和取消语完全跳过分类器：验证码是答案，「取消」绝不能等一次分类往返。

### 派发决策移出聊天串行队列

队列存在的唯一理由是内核拒绝在同一会话并发 `prompt()`——但**路由**决策（draining 检查、名册/RBAC、前台 escape、规划旁路、worker 派发）全都在队列**里面**做。inline 回合挂死时，下一句话连分诊都进不了。`IMManager.handle()` 现在把所有路由决策放在入队**之前**；只有 inline 执行本体（看门狗 + `engine.send`）仍然串行。新任务在 inline 挂死时 ~5 毫秒完成派发；普通问句保持 FIFO。

### 真正生效的 per-profile 更新缓存隔离

这个修复背后的现场事故：盒子三个 profile 共享**同一个**更新 pending 目录，下载中途互相删除（全家族 ENOENT），两次失败触发了更新熔断。根因是 `isolateUpdaterCache` 守卫调用了 `setUpdaterCacheDir()`——一个在 electron-updater 6.8.9 里**不存在**的 API——于是每个 profile 都静默返回，什么也没隔离。修复改为给 `autoUpdater.downloadedUpdateHelper` 预置隔离目录，这是 6.x 真实代码路径会走的结构。新规则：隔离要么**发生**（INFO 带目录名），要么**说明**（WARN 带原因）——静默返回正是这个 bug 的形状。

### 用户追加消息刷新进度推送预算

同一个 5 小时任务，第二个缺陷：第 20 条推送在 20:09 落地后，之后每个 pump 节拍都被 `progress push cap (20) reached` 拦下——永久静默。cap 防的是「没人看时的刷屏」，而主动 steer 任务的用户恰恰在场。被接受的追加消息现在**原地刷新**该 run 的预算（日志 `progress budget reset by user follow-up (was N/M)`），不需要结束任务——已烧完配额的 run 在用户下一条消息时立即恢复推送。只重置 cap 计数：degraded-LLM 退避是链路健康机制，保持独立。被抑制的预算现在**零成本**：cap 检查移到旁路 summarize 之前，被 cap 的节拍不再为打一行日志烧一次有界模型调用（盒子此前每 10 分钟白烧一次，持续数小时）。

合并后代码门禁：**145 套件全过**、双 typecheck 零错、不可变内核闸门报告 16 守护区未变。

现场验证边界：已在测试中对真实 Agent 循环与真实 updater 模块验证；部署盒子走自己的升级通道。
