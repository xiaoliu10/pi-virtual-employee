# v0.2.200

## English

### Router/Worker is infrastructure again, not a task type

A group chat message — "最近7天的对账结果统计，报表要带查看链接" — self-scheduled itself for `2026-11-07 00:50` and pushed its completion wearing the autonomous-task template (「下次跟进 / 跟进原因」). One conversation message had become an autonomous task, and the user had said more than once that these are different things.

The root cause was structural, not a model misbehaving: chat dispatches were creating rows in `work_items`, the phase-1 design decision ("Worker container: reuse work item, don't build a second engine") put them in the autonomous-task table, state machine, prompt and protocol. Every boundary then had to be defended by a prohibition — no scheduled tasks, no mining, no NEXT_CHECK — three layers of prompt teaching, engine interception and tests per rule, each one a leak away from another incident.

- **`worker_tasks`**: a linear state machine (`queued → running → done | cancelled`) in its own table. The autonomous columns (`next_check_at`, `cadence_ms`, `resident`, streaks) do not exist there — not prohibited, absent.
- **`WorkerService`**: a worker is one persistent durable conversation (`worker:<id>`), and its lifecycle is driven by code events: the durable turn settling IS completion. The result is the session's final assistant text, extracted by code — no marker parsing anywhere.
- **Markers are inert**: `[[NEXT_CHECK]]` written in a worker session is plain text that gets pushed verbatim, because no code here looks for it. That inertness is the structural separation, and it is pinned by tests (`PRAGMA table_info` assertions, marker pass-through).
- **Follow-ups are conversation, not state**: a message from the source conversation continues the SAME durable session as a new turn; a finished worker stays finished. There is no `waiting_human` pause state — a worker that needs a human just says so in its reply.
- **Router dispatch rewritten**: task-shaped messages spawn workers; messages arriving on a conversation with an existing worker are injected into it. No work_items rows are created. The admin gate is gone — Worker is dialogue infrastructure, and RBAC already governs the send path per actor.
- **「前台执行」 escape, worker edition**: cancels this sender's queued-or-running worker (aborting a live durable round) and re-runs the original instruction inline. `cancelled` is a legitimate linear terminal.
- The transitional layer is deleted: the `oneShot` prompt branches and the chat-origin NEXT_CHECK gate were defending a state that no longer exists.

### One browser per profile, many tab owners

The box-side playwright shim was clone-on-use, and its busy check matched directory names by substring. A leftover clone's directory contained the master's name, so every new task failed with `PROFILE_MASTER_BUSY` while the master sat idle.

- `ve_pw_profile_lock.py` v5.1 is attach-or-host: an existing `DevToolsActivePort` that answers over CDP means *attach* (a fresh tab in the shared browser, `close()` closes only your own tabs then disconnects); no endpoint means *launch as host* with `--remote-debugging-port=0`, so later tasks can find it. Two-strike stale sweep, no `atexit` close (the event loop is already stopped by then).
- Real-Chromium end-to-end verified on the box: A hosts → B reports `TabContext` and sees only its own page → A exits → C re-hosts on the same profile.
- `resources/browser-bridge` ships the shim and its python unit tests behind `scripts/test-pw-shim.mjs`; a machine without python3 fails the suite rather than silently skipping it.
- Discipline rewritten in the immutable prompt block: browser concurrency means tabs in one shared browser — no profile clones, no `connect_over_cdp`, and `taskkill` on a browser is an incident, not a cleanup.

### Progress notes that never arrived now explain themselves

An 85-minute work window produced zero progress pushes and **zero log lines**. Three paths were silent: installing the timer, the first degraded push, and every successful push. "Did the notifier even fire?" was unanswerable from the log.

- `progress notifier started: interval=Nmin target=…`, `progress brief degraded (side LLM unavailable)`, and `progress pushed #N to <target>` are all logged now.
- `taskProgressMin` (work-window cadence, default 30) and `longTaskProgressMin` (chat-turn heartbeat) were easy to confuse; the box was configured for the latter while the former governed windows.

## 中文

### Router/Worker 回归基础设施，不再是一种任务类型

群里一句话——「最近7天的对账结果统计，报表要带查看链接」——把自己排程到了 `2026-11-07 00:50`，完成推送还套用了自主任务的模板（「下次跟进 / 跟进原因」）。一条对话消息变成了自主任务，而用户已经反复说过这是两类东西。

根因是结构性的，不是模型越权：对话派发在 `work_items` 里建行，第一期的设计决策（「Worker 容器：复用 work item，不造新引擎」）把它们放进了自主任务的表、状态机、prompt 和协议里。于是每条边界都只能靠禁止规则防守——禁建定时任务、禁挖掘、禁 NEXT_CHECK——每条都要 prompt 教导、引擎拦截、测试守护三层，漏一层就是又一次事故。

- **`worker_tasks`**：独立表里的线性状态机（`queued → running → done | cancelled`）。自主任务那套列（`next_check_at`、`cadence_ms`、`resident`、streak）在那里**不存在**——不是被禁止，是没有。
- **`WorkerService`**：一个 worker 就是一个持久 durable 会话（`worker:<id>`），生命周期由代码事件驱动：durable 回合结算即完成。结果由代码从会话最终 assistant 文本提取——任何地方都不解析标记。
- **标记是惰性的**：worker 会话里写 `[[NEXT_CHECK]]` 只是普通文本，原样推送出去，因为没有代码去找它。这种「不可达」就是结构区分，并由测试钉死（`PRAGMA table_info` 断言、标记透传）。
- **追问是对话，不是状态**：来源会话的消息续进**同一个** durable 会话的新回合；已完成的 worker 保持完成。没有 `waiting_human` 挂起态——需要人的 worker 直接在回复里说。
- **Router 派发重写**：任务型消息派发 worker；来源会话已有 worker 的消息注入其中。不再创建 work_items 行。管理员门槛移除——Worker 是对话基础设施，权限本就由发送路径的 RBAC 按 actor 治理。
- **「前台执行」逃逸（worker 版）**：取消本人派发的排队中/执行中 worker（abort 活跃 durable 回合），原始指令 inline 重跑。`cancelled` 是合法的线性终态。
- 过渡层删除：`oneShot` prompt 分支与 chat origin 的 NEXT_CHECK 闸门，防守的是已不存在的状态。

### 一个浏览器多标签页

盒子上的 playwright shim 原本是 clone-on-use，占用检测按目录名子串匹配。残留 clone 的目录名包含 master 名，于是 master 明明空闲，每个新任务却都 `PROFILE_MASTER_BUSY`。

- `ve_pw_profile_lock.py` v5.1 改为 attach-or-host：`DevToolsActivePort` 存在且 CDP 可连即**附着**（在共享浏览器里开新标签页，`close()` 只关自己的页再断开）；没有端点则**作为宿主启动**并带 `--remote-debugging-port=0`，后续任务才找得到它。两击清扫残留、去掉已失效的 `atexit` 关闭。
- 盒子真 Chromium 端到端验证：A 当宿主 → B 报告 `TabContext` 且只看到自己的页 → A 退出 → C 在同一 profile 重新当宿主。
- `resources/browser-bridge` 随包发 shim 及其 python 单测，由 `scripts/test-pw-shim.mjs` 桥接；没有 python3 的机器会让套件失败，而不是静默跳过。
- 不可变 prompt 纪律改写：浏览器并发 = 一个共享浏览器的多个标签页——不克隆 profile、不自己 `connect_over_cdp`、对浏览器 `taskkill` 属于事故而非清理。

### 没送到的进度汇报现在会自己说明原因

一个跑了 85 分钟的工作窗口，零条进度推送、**零行日志**。三处静默：安装定时器、首次降级推送、以及每一次成功推送。「notifier 到底有没有触发」从日志上无从回答。

- 现在会记录 `progress notifier started: interval=Nmin target=…`、`progress brief degraded (side LLM unavailable)`、`progress pushed #N to <target>`。
- `taskProgressMin`（工作窗口节奏，默认 30）与 `longTaskProgressMin`（聊天轮心跳）容易混淆；盒子上配置的是后者，而窗口由前者控制。
