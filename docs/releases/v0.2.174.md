# v0.2.174 — Fix: recovered work reported into a conversation nobody opens

## English

### The question this answers

"Recovery is supposed to work on the durable kernel — why has no restart ever recovered a task?"

Two separate facts, and only one of them was a defect.

### Not a defect (and a correction to our own earlier note)

A graceful close does **not** silently drop in-flight work. `pi-durable`'s `join()` aborts each invocation, waits, then writes its task back as `pending` — *"a close is not a crash"*. So an upgrade mid-tool does leave recoverable work, and the next open replays it. An internal note claiming "a graceful stop leaves nothing to recover" was wrong; recovery **was** running.

### The defect

The recovered answer was pushed only when `history.isReadOnly(conversationId)` was true. Window conversations — `work:<itemId>`, `sched:<taskId>:<runId>` — are neither read-only nor watched by anyone, so a recovered task finished its turn and reported into a console conversation nobody opens. From the operator's side: "recovery never happened."

### Changes

- New `src/engine/durable/recovered-delivery.ts`: routing is a pure, tested decision.
  - `planRecoveredDelivery()` — **direct** (IM conversations, unchanged), **task-source** (work → its `origin_conversation`, else a `dt:` 1:1 with the creator; scheduled → the task's own conversation), **none** (malformed ids stay silent and specifically never fall back to the console conversation, which was the bug).
  - `resolveTaskSourceTarget()` — resolves the owning row into a concrete target, or **skips with a stated reason** when the row is gone or has no conversation.
  - `formatRecoveredNote()` — prefixes `♻️ … 崩溃后已自动恢复并完成本轮`. An answer arriving hours late without that marker reads as a hallucination.
- A recovered work window now **closes its own state machine**: the turn completed, but the runner that would have called `setStatus` died with the process, leaving the item in `working` — invisible to `listDue()`, with `nextWakeAt()` returning `undefined`, i.e. a task that silently never runs again. Recovery now reschedules it one minute out, like a normal close.

### Verification

`scripts/test-recovered-delivery.mjs` (7 cases) covers routing, target resolution, skip-with-reason, malformed-id silence and the note format. Mutation checks: reverting windows to the old `direct` behaviour → 2 red; dropping the recovery marker → 1 red. Full gate: 70 suites, typecheck, build, immutable.

> An earlier attempt at this fix (skip-list) was reverted after review: it parked recovered items in `working` forever, which is worse than asking a human. Recorded here because the failure mode — "a fix that makes the stuck state unrecoverable" — is worth remembering.

## 中文

### 这篇回答的问题

「内核切 durable 后应该有中断恢复，为什么几次升级重启都没恢复过任务？」

两件不同的事，其中只有一件是缺陷。

### 不是缺陷（并修正我们自己的错误说法）

优雅关闭**不会**悄悄丢掉在飞的工作。`pi-durable` 的 `join()` 会 abort 每个 invocation、等它们结束，再把任务写回 `pending`——注释原文「a close is not a crash」。所以升级中途确实留下可恢复的工作，下次启动会重放。我们内部此前那句「优雅停止没有遗留可恢复」是错的：恢复**一直在跑**。

### 真正的缺陷

恢复出来的答案只在 `history.isReadOnly(conversationId)` 为真时才推送。而窗口会话——`work:<itemId>`、`sched:<taskId>:<runId>`——既不是只读、也没人看，于是恢复完成的那一轮把结果写进了一个没人打开的控制台会话。从操作者视角：**「根本没恢复」**。

### 变更

- 新增 `src/engine/durable/recovered-delivery.ts`，路由变成可测的纯决策：
  - `planRecoveredDelivery()`——**direct**（IM 会话，行为不变）、**task-source**（work → 来源会话，兜底创建人 `dt:` 单聊；scheduled → 任务自己的会话）、**none**（畸形 id 一律安静，**绝不**回落到控制台会话，那正是本 bug）
  - `resolveTaskSourceTarget()`——把归属行解析成具体目标；行已删或无会话时**跳过并给出原因**
  - `formatRecoveredNote()`——加「♻️ …… 崩溃后已自动恢复并完成本轮」前缀。几小时后突然冒出一条答案不标注，会被当成模型幻觉
- 恢复过的 work 窗口现在**自己收尾状态机**：那一轮的工作做完了，但本该调用 `setStatus` 的 runner 随进程一起没了，item 停在 `working`——`listDue()` 看不见它，`nextWakeAt()` 返回 `undefined`，任务从此静默不再运行。恢复现在把它按正常收尾顺延一分钟后重开。

### 验证

`scripts/test-recovered-delivery.mjs` 7 条，覆盖路由、目标解析、跳过并给原因、畸形 id 静默、恢复文案。变异验证：窗口退回旧的 `direct` 行为 → 2 红；去掉恢复标注 → 1 红。全量门禁 70 套件、typecheck、build、immutable 通过。

> 本修复的第一版（skip 名单）经审查后已回滚：它把恢复过的 item 永久停在 `working`，比让人介入更糟。这里记下来，是因为这个失败模式——「修复反而制造了不可恢复的卡死」——值得记住。
