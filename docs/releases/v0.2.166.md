# v0.2.166 — 崩溃恢复第二片：副作用恢复核实 + IM 投递账本 + UI 增量重连

durable 崩溃恢复（#116）落地后的第二片，聚焦三件事：副作用工具中断后的恢复纪律、IM 出站投递的崩溃安全、控制台与主进程之间的增量同步。

## 有副作用工具的恢复核实（phase 3）

- 新增 `src/engine/durable/recovery-policy.ts`：每个工具按外部效果分类恢复策略——`retry`（幂等，如 `save_document`）、`verify`（结果不确定时先核实业务状态再决定，如 `save_report`/`provide_document`/定时任务系列/`delete_files`）、`manual`（无法核实，停下问人，如 `run_command`/`computer_use`/浏览器操作）。未收录工具默认 `manual`：新工具不经审查永远不会被自动重跑。
- 新增 `src/engine/durable/interrupted-notice.ts`：durable 对中断工具只写一行 "may have partially run"，模型拿到后最常见的下一步恰恰是盲目重试。该扩展在 `afterTool` 把这类结果改写为带核实指令的恢复提示（已完成则复用、确认未完成才执行、无法确认则人工核实）。
- `ve-tools.ts`：unsafe 工具执行抛错时，不再把裸堆栈交给模型（它会自己重试），改为返回恢复提示 + 原始错误。

## 收尾门禁三处修复（审查发现）

- **工具证据误判**：验证轮的工具调用在前一条 assistant 消息里，最终回答永远不含 toolCall——真实验证过却被判"无证据"。改为 `afterTools` 记录本 run 是否真用过工具。
- **运行身份**：实测 `{ continue }` 注入会产生新 `taskId`，按 taskId 隔离会让防死循环计数永不累积。改为注入链身份：门禁注入后的下一轮属于同一逻辑 run；新 run 启动时清理崩溃残留条目。
- **能力校验**：hook api 的 `commit/snapshot` 缺失时告警一次（fail-open，但可诊断），不再静默吞掉。

## IM 投递账本（delivery ledger）

- 新增 `src/im/delivery-ledger.ts`（`push_ledger` 表，occurrence 身份）：推送前 claim、成功 delivered、失败 failed 可重试；同 occurrence 已 delivered 永久跳过——重启后不会把同一次运行推两遍。
- 定时任务/自主链/聊天回复分别用 `sched:<taskId>@<runId>`、`chain:<conv>:<startedAt>`、`chat:<channel>:<msgId>#hb-<时间桶>` 派生身份；聊天进度心跳按 15 分钟时间桶抑制重复（与 ProgressNotifier 间隔一致），正常周期心跳不受影响。
- 无 occurrence 的推送行为不变；90 天自动清理终态行。

## UI 增量同步

- 控制台聊天页此前每次 IM 活动信号都全量重拉会话消息；改为游标增量（`tasks:messagesSince`），按 id 幂等合并，长会话重连不再整段重传重渲染。

## 已知边界（如实声明）

- durable 宿主当前仍以 `durable` 内核灰度开关运行，真实会话的 `EmployeeEngine.send()` 尚未路由到 durable（下一片）；本版的恢复纪律作用于 durable 灰度面与 legacy 错误恢复路径。
- 门禁注入链身份存在进程内状态：崩溃后恢复的验证轮会重新计数（fail-open 方向：宁可多验证，不会错误放行）。

## 验证

- 全量门禁：60 套件通过；双 tsconfig typecheck、build、immutable 通过。
- 新增测试：恢复策略分类与中断通知、真实门禁的证据/隔离行为（含跨重启持久化）、SIGKILL 恢复测试加固（拒绝 `unknown` 终态、要求 pre-resume pending 与中断结果入上下文）、投递账本 9 例。
