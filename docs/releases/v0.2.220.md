# v0.2.220

## English

### Context lifecycle management — compaction as a structural guarantee, not a failure response

Field ruling: automatic context compaction is a basic agent capability. Two same-day incidents (a worker session that accumulated a full day of browser automation — 416 tool calls — hit the model's hard 200k-token wall twice) exposed that context was managed by after-the-fact rescue, not by structure. Three fixes:

- **Pre-turn budget gate.** A turn must never START over budget: before the first request, if the transcript estimate is over the usable-window line, the engine shrinks it first (compaction → fit verification → outright truncation, with honest failure). Together with the mid-turn gate and the overflow recovery this forms three lines of defense. Applies to every long-lived conversation. (Also fixed a latent NaN bug that would have silently disabled every budget gate.)
- **Done-worker injection windowing (default reversed).** A finished worker is history: by default every message falls through — a fresh task spawns a fresh worker born with a bounded excerpt of the source chat, and other messages are answered by the foreground conversation from its full push history. Only a conversational follow-up (「结果呢」/「继续」) within 30 minutes of the worker settling keeps the dialogue. This is what made tonight's incident possible: a fresh lookup task was routed as "conversational follow-up" into a worker that had finished four hours earlier, injecting a day-long transcript.
- **Task detection for the most common ops verb.** 「查」 joined the task-verb list, and a ≥10-digit serial (order/流水 number) now counts as task cargo — a lookup task like 「帮我查一下这笔流水：0422… 的支付渠道下单日志」 is routed as a task (fresh worker / planned foreground turn), not as chat.

## 中文

### 上下文生命周期管理——压缩成为结构性保证，而非失败后的补救

现场裁定：自动压缩上下文是 agent 最基本的能力。同一天两起事故（一个 worker 会话累积了整天浏览器自动化——416 次工具调用——两次撞上模型 20 万 token 硬上限）暴露出上下文管理靠的是事后补救而非结构性保证。三项修复：

- **入轮预算门。** 任何回合不得在超预算的账本上启动：第一条请求发出前，transcript 估算超出可用窗口线就先收缩（压缩→fit 校验→硬截断，含诚实失败）。与回合中门、溢出恢复构成三道防线。对所有长寿命会话生效。（顺带修掉一颗会让所有预算门静默失效的 NaN 隐患。）
- **done-worker 注入窗口化（默认反转）。** 结束的 worker 是历史：默认一切消息 fall through——新任务派发全新的 worker（出生携带来源会话的有界摘录），其他消息由 foreground 会话用完整推送历史作答。只有 worker 结束后 30 分钟内的对话性 follow-up（「结果呢」/「继续」）才延续原对话。今晚事故的入口正是这里：一个全新查询任务被当成「对话性 follow-up」注入了 4 小时前结束的 worker，把一整天的账本接了进去。
- **最高频运维动词的任务判定。** 「查」进入任务动词表，≥10 位数字串（单号/流水号）算任务标的物——「帮我查一下这笔流水：0422… 的支付渠道下单日志」这类查询会被当作任务派发（全新 worker / 有计划的前台回合），而不是当成闲聊。
