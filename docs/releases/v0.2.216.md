# v0.2.216

## English

### Packaging integrity gates — the v0.2.215 startup-freeze incident can never ship again

Field incident (2026-11-10): the v0.2.215 Windows installer was built from a release worktree whose `node_modules` was a **symlink** to the main checkout. electron-builder's node-module collector shells out to `npm list -a`, which mis-resolves a symlinked `node_modules` and reports thousands of bogus `missing:`/extraneous entries; the collector's production dependency graph collapsed (`depCount=27` instead of several hundred) and the packaged `app.asar` shipped with only ~1,500 files instead of ~12,000 — every transitive dependency missing (`zod`, `bindings`, `@babel/runtime`, `@protobufjs/*`, `accepts`, …). The installed app died at startup on `Cannot find module 'bindings'` and sat on an **invisible error dialog** — on an unattended machine that looks exactly like a silent hang. Nothing in the build failed loudly: the collector logged a single debug line.

Two structural gates now make this failure mode impossible to ship:

- **Build-environment guard** (`scripts/check-build-env.mjs`): `package:win` / `package:mac` / `package:linux` refuse to run when `node_modules` is a symlink, with the incident story and the remediation paths (build from a real checkout, or materialise the worktree with `npm ci`).
- **asar integrity gate** (`scripts/verify-asar.mjs`): after electron-builder finishes, the produced `app.asar` must pass file-count (≥6,000 vs broken ~1.5k), top-level package count (≥40 vs broken ~24) and a runtime-critical invariant list (`bindings`, `zod`, `@babel/runtime`, the four `@earendil-works` engine packages, `electron-updater`, `dingtalk-stream`, `playwright`, …, `dist-electron/main.js`) — otherwise the `package:*` chain fails before any artifact can be uploaded. Both gates were validated against the actual broken v0.2.215 asar (rejected) and the healthy v0.2.214 asar (passed).

## 中文

### 打包完整性闸门 —— v0.2.215 启动冻结事故无法再次发出去

现场事故（2026-11-10）：v0.2.215 的 Windows 安装包在发版 worktree 中构建，而该 worktree 的 `node_modules` 是指向主 checkout 的**符号链接**。electron-builder 的 node-module collector 依赖 `npm list -a`，后者在 symlink 化的 `node_modules` 上解析错乱，报出数千条虚假的 `missing:`/extraneous；collector 的生产依赖图塌缩（`depCount=27`，正常应为数百），打包出的 `app.asar` 只带约 1,500 个文件（正常约 12,000）——所有传递依赖缺失（`zod`、`bindings`、`@babel/runtime`、`@protobufjs/*`、`accepts` 等）。安装后的应用启动即死于 `Cannot find module 'bindings'`，并停在一个**看不见的错误对话框**上——在无人值守的机器上，这与静默挂起完全无法区分。构建全程没有任何报错：collector 只打了一行 debug 日志。

两道结构性闸门让这种失败形态永远无法再发出去：

- **构建环境守卫**（`scripts/check-build-env.mjs`）：`package:win` / `package:mac` / `package:linux` 在 `node_modules` 为符号链接时拒绝打包，并附事故原委与两条整改路径（在真实 checkout 构建，或用 `npm ci` 实体化 worktree）。
- **asar 完整性闸门**（`scripts/verify-asar.mjs`）：electron-builder 结束后，产出的 `app.asar` 必须通过文件数（≥6,000，残缺约 1.5k）、顶层包数（≥40，残缺约 24）与运行时关键不变式清单（`bindings`、`zod`、`@babel/runtime`、四个 `@earendil-works` 引擎包、`electron-updater`、`dingtalk-stream`、`playwright`、`dist-electron/main.js` 等）校验——任一不过，`package:*` 链条在任何产物可被上传之前失败。两道闸门均用真实的 v0.2.215 残缺 asar（拒绝）与健康 v0.2.214 asar（通过）验证。
