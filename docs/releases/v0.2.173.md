# v0.2.173 — Fix: task-progress notes never arrived on the durable kernel

## English

### Field report

After installing v0.2.172 a group still received **no** task-progress note. The notifier itself was fine — v0.2.171's wiring was in the shipped bundle. The problem was every **gate** in front of it: all of them evaluated to false, and every one failed **silently**.

### Root cause

1. **`isRunning` read `agent.state.isStreaming`.** Since v0.2.167 the durable kernel is the default: `engine.send` returns through `durableRuntime.send`, which drives the harness directly. `pi-durable` never sets that flag (only pi-agent-core's own `prompt()/stream()` do), so it was false for the entire run and every tick returned early — for scheduled tasks, work-item windows **and** the autonomous-chain heartbeat.
2. **Work-item targets only used `origin_conversation`.** The fallback was a bare `created_by` staffId, which is not a conversation id — `adapterFor` accepts only `dt:`, so delivery failed after the side LLM pass had already been paid for.
3. **The scheduled-task preflight probed with an empty string.** `shouldPushScheduledResult(task, undefined, "")` rejects empty text, so that gate was permanently closed.
4. **`start()` returned without a timer and without a log line** when there was no target — the exact silence that made a shipped feature look absent.

### Changes

- New `src/scheduler/progress-wiring.ts`: `createWorkProgressNotifier` / `createRunProgressNotifier` / `resolveWorkProgressTarget`. Liveness is the **caller's** lifetime (window not stopped, run not settled), never the kernel's internal stream flag; targets fall back to `dt:<staffId>`; the preflight probe is non-empty.
- `DurableRuntime.isBusyConversation(id)` + `engine.isConversationStreaming()` now ask the kernel first — this also fixes steer checks that were silently reporting "idle" for every durable turn.
- `progress-notify`: not-started (no target / interval 0) and every gate-dropped beat now log one line with the reason.

### Verification

`scripts/test-progress-wiring.mjs` (5 cases): a durable session with no `isStreaming` still pushes; a source-less item falls back to a `dt:` 1:1; a scheduled run pushes on its own lifetime and stops spending summaries once settled; silent/dead/target-less notifiers each log why; the kernel's per-conversation busy query tracks submissions. Mutation checks: reverting the `isStreaming` gate → 2 red; empty preflight probe → 1 red; dropping the `dt:` prefix → 1 red; silent not-started → 1 red; `isBusyConversation` always false → 1 red. Full gate: 69 suites, typecheck, build, immutable.

## 中文

### 现场

装了 v0.2.172 之后，群里**仍然收不到**任何任务进度推送。notifier 本身没问题——v0.2.171 的接线确实在包里。问题出在它前面的每一道**门**：全部恒假，而且**全部静默**。

### 根因

1. **`isRunning` 读 `agent.state.isStreaming`**。v0.2.167 起 durable 内核是默认：`engine.send` 走 `durableRuntime.send` 直接驱动 harness，而 `pi-durable` 从不置这个标志（只有 pi-agent-core 自己的 `prompt()/stream()` 会）。于是整个 run 期间恒 false，每次 tick 静默早退——定时任务、工作项窗口、以及自主链心跳全部中招。
2. **工作项 target 只取 `origin_conversation`**。兜底是裸 `created_by` staffId，那不是会话 id（`adapterFor` 只认 `dt:`），推送必然失败，而旁路 LLM 已经付过费了。
3. **定时任务 preflight 用空字符串探测**。`shouldPushScheduledResult(task, undefined, "")` 对空文本一律拒绝，这道门因此永久关闭。
4. **没有 target 时 `start()` 直接返回**，既不装定时器也不打日志——正是这种静默让一个已发布的功能看起来从未存在。

### 变更

- 新增 `src/scheduler/progress-wiring.ts`：「是否还在跑」由**调用方**的生命周期决定（窗口未 stop、run 未结束），不再读内核内部标志；target 兜底 `dt:<staffId>`；preflight 用非空探针。
- `DurableRuntime.isBusyConversation(id)` + `engine.isConversationStreaming()` 改为先问内核——顺带修复了 steer 判断在 durable 下一直报「空闲」的问题。
- `progress-notify`：没启动（无 target / 间隔 0）与每次因门被丢弃，都会打一行带原因的日志。

### 验证

`scripts/test-progress-wiring.mjs` 5 条：durable 会话（无 `isStreaming`）仍推送；无来源会话兜底 `dt:` 单聊；定时任务按自身生命周期推送并在结算后停止烧摘要；静默/已结束/无 target 各自留下原因日志；内核按会话的忙碌查询随提交跟踪。变异验证：改回 `isStreaming` 门 → 2 红；preflight 空串 → 1 红；去掉 `dt:` 前缀 → 1 红；不启动不打日志 → 1 红；`isBusyConversation` 恒 false → 1 红。全量门禁 69 套件、typecheck、build、immutable 通过。
