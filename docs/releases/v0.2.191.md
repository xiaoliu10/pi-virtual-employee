# v0.2.191

**English**

### Upgrading to 0.2.190 broke every existing install's task queue (P0)
- `priority` was added to `CREATE TABLE` but not to the migration block. The table is created with `IF NOT EXISTS`, so an existing database is never rebuilt — every profile upgrading to 0.2.190 had no such column, and the first write threw `no such column: priority`.
- It went unnoticed because every test builds its fixture from `CREATE TABLE` (which always carries the newest columns). Only an in-place upgrade exercises the `ALTER` path, and nothing tested it.
- Fixed, and the migration is now a testable function driven against a frozen pre-0.2.190 table, asserting that **no declared column is lost** — not just this one.

### Chat dispatch is now on by default
- The gray release validated the chain end to end, so dispatch no longer needs a switch.
- Legacy configs that never stored the key inherit the new default; an explicit `false` still opts out.
- Only a message whose plan has **≥2 numbered steps + a long-running verb + an admin sender** is handed to the background. Questions, single-step commands and non-admin senders stay inline.

### Workers run concurrently (5 per profile)
- This had to land **before** dispatch could default on. The window runner was strictly single-window, so routing chat tasks to it would have serialised the entire profile — strictly worse than the per-conversation queue it replaced (two chats could previously run in parallel).
- Windows now enter a bounded pool of 5, each independently tracked.
- Three defects in the first implementation were caught by tests:
  - a **re-entrancy race** that admitted 5 windows despite a cap of 2 (a window that settled instantly deleted itself mid-loop, so the counter never grew);
  - a **non-idempotent wake timer** that stacked two timers for the same instant;
  - a **shutdown deadlock** — `stop()` awaited in-flight sends, so any session that ignores abort hung teardown.

### A non-admin's task is no longer acknowledged and then dropped (P1)
- The dispatch path returned a courtesy warning ("this will continue in the session"), and the caller treats any non-empty result as "dispatched" — a viewer's task was acknowledged in text and never executed.
- It now falls through to inline execution. The bug predates this release but was masked by the default-off switch.

**中文**

### 升级到 0.2.190 打坏了所有既有安装的任务队列（P0）
- `priority` 加进了 `CREATE TABLE` 却漏了迁移块。建表用 `IF NOT EXISTS`，既有数据库不会重建——每个升级到 0.2.190 的 profile 都没有这一列，第一次写入就抛 `no such column: priority`。
- 测试没抓到，是因为所有 fixture 都用 `CREATE TABLE` 建表（永远带最新列）。只有「原地升级」才走 `ALTER` 路径，而这条路径没有任何测试。
- 已修复，并把迁移抽成可测函数，用冻结的 0.2.190 之前的表结构驱动，断言升级后**不丢任何声明的列**——不只这一个。

### 聊天任务转后台改为默认开启
- 灰度验证了整条链路，不再需要手动开开关。
- 从未保存过该项的旧配置继承新默认；显式设为 `false` 仍然关闭。
- 只有「**规划 ≥2 编号步骤 + 含耗时动词 + 管理员发起**」的消息才转后台。问答、单步命令、非管理员一律留在前台。

### Worker 支持并发（每 profile 5 个）
- 这件事必须在默认开启**之前**落地。窗口执行器原本严格单窗口，把聊天任务导过去会让整个 profile 串行——比它替代的「按会话排队」更糟（原来两个会话可以并行）。
- 现在窗口进入上限为 5 的池子，各自独立跟踪。
- 第一版实现里的三个缺陷都被测试抓到：
  - **重入竞态**：上限设 2 却起了 5 个（瞬间完成的窗口在循环中途把自己删掉，计数永远长不起来）；
  - **非幂等唤醒定时器**：同一到期时间叠了两个定时器；
  - **关停死锁**：`stop()` 等待 in-flight send，遇到不响应 abort 的会话就挂住。

### 非管理员的任务不再「回执后消失」（P1）
- 派发路径返回一句客气的警告（「该任务将继续在会话内执行」），而调用方把任何非空返回都当作「已派发」——普通成员的任务被文字确认后再也不执行。
- 现在正确落回前台执行。该缺陷在本次之前就存在，只是被「默认关闭」的开关挡住了。
