# v0.2.219

## English

### Chat progress reporting works again — the pump could never see a busy conversation

An inline chat task ran 13+ minutes of dense tool calls while the global progress pump's every 5-minute tick logged `busy=0 actions=none` — not a single side-channel progress report was ever pushed. A field note from 2026-11-06 had already recorded "the chat pump never fired since v0.2.192"; this is the deterministic root cause: `engine.busyConversations()` consulted ONLY the durable runtime, and after the 0.2.214 single-kernel decision the legacy kernel is the default and the durable runtime is never constructed — so the pump's view of "busy" was permanently an empty array. The live signal was always there: pi-agent-core keeps `isStreaming=true` for the whole `prompt()` call, and `retryWaits` covers deliberate backoff windows. `busyConversations()` now reports both; a regression test pins that streaming and backoff sessions appear in `busy` and clear once the work ends.

## 中文

### 聊天进度汇报恢复了——进度泵从来就看不见「忙碌」的会话

一个内联 chat 任务连续跑了 13+ 分钟的密集工具调用，而全局进度泵每 5 分钟的 tick 日志全是 `busy=0 actions=none`——一条旁路进度汇报都没发过。2026-11-06 的现场注记早已记下「chat pump 自 v0.2.192 起从未 fire」，本次找到确定性根因：`engine.busyConversations()` 只读 durable runtime，而 0.2.214 单内核裁定后默认 legacy 内核、durable runtime 根本不再构造——泵眼里的「忙碌」永远是空数组。存活信号其实一直都在：pi-agent-core 在整个 `prompt()` 期间保持 `isStreaming=true`，`retryWaits` 覆盖有意退避窗口。现在 `busyConversations()` 把两者都报上来；回归测试钉住「streaming 与退避中的会话都出现在 busy 里、工作结束即清空」。
