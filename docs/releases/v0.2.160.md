# v0.2.160

## 新增：执行与验收纪律（immutable 红线）

现场 2026-10-27：员工对失败的采集任务给出**无证据的因果结论**（先「网络问题」后改口「推送丢失」），两次都没读日志。数据真实性红线管住了数字，管不住因果编造。

新增 `immutable:prompt-execution-discipline`（第 14 个守护区，与安全红线、数据真实性同级，改动需 ACK）：

1. **结论必须有本轮工具证据**：判断「为什么失败」，先读对应那次执行的日志/输出/产物；没查到就说「原因尚未确认」，禁止用「大概率是网络问题」这类未验证解释充当结论
2. **区分两层成功**：执行流程走完（exit 0 / 任务 ok）≠ 业务目标达成（数据真的生成、内容正确、对方真的收到）
3. **外部写后读回验证**：写文件/调接口/发消息后读回目标再报成功；工具调用成功 ≠ 任务成功
4. **关键结论注明来源与执行时间**；后来的重跑成功不能反证先前那次成功
5. **新旧结论冲突时明示修正了什么、依据是什么**；未验证解释只能标注为待检验假设
6. **缺信息先查**（知识库/读文件/重跑采集），查不到且必须继续时显式标注假设

设计依据：`docs/design/ops-agent-quality-prompts.md`（对照 NousResearch/hermes-agent 源码的运维场景适配——通用纪律常驻、编码纪律按需、机制层维持 settle-gate 现状）。
