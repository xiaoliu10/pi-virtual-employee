## 0.2.105

### 改进

- **自主跟进节奏防退化**（#18，现场反馈：对账巡检把跟进固定在每天 16:30，事实上退化成了定时任务）：`NEXT_CHECK` 时间必须有**外部依据**（数据何时生成/上次发现什么），无异常拉长、有异常缩短、非工作日跳过，禁止不加思考写「明天同一时间」。新增确定性例行检测 `fixed_streak`：连续按 ~24h 相近时段跟进则累计（≥2 次窗口内注入【节奏警示】要求重新评估，≥3 次推送中建议管理员改用定时任务）；上次跟进时间与原因持久化并回注窗口前缀。本质是每日例行的巡检仍建议用定时任务（#15 自主模式）；工作项留给需要判断力的跟进。

### 修复

- **知识库保存/归档条目报 `no such table: kb_vec`，更新已有条目时还会破坏其检索索引**（现场 2026-10-01：自主任务完成把踩坑沉淀进知识库时报错，条目未落库）。根因有两层：
  - `kb_vec` 向量表是**惰性创建**的——只在 embedding 供应商配置齐全时由首次索引创建；sqlite-vec 扩展加载正常但供应商未配齐的部署里该表始终不存在。此前纯 BM25 检索完全正常、新建条目也正常（清理钩子对空 chunk 列表提前返回，从不触碰向量表），所以问题长期潜伏。
  - `saveLearned` 按**标题精确匹配**更新已有条目（或归档/合并/删除）时，第一次真正执行向量清理 `deleteByRowids(非空)`——它只判断「扩展是否可用」而不判断「表是否存在」→ 抛错。更糟的是抛错点位于「删旧 chunks 之后、插新 chunks 之前」，被更新的条目内容已改但检索 chunks 被删光，从检索中消失。
  - 修复：`VecStore` 的删除/清理/写入/检索在表不存在时安全 no-op（每次核对 `sqlite_master`，兼容导入恢复等外部删表）；`dimensions <= 0` 的 embedding 配置视为未配置，干净降级纯 BM25，不再进入「建表跳过 → 写入报错 → 整批标失败」的重试循环。新增 `test-vec-store.mjs`（4 用例）与 `test-knowledge-store.mjs`（4 用例）钉住全部机制。
  - **升级后恢复动作**：0.2.104 期间更新过的知识条目若搜索不到，对同一标题重新保存一次即可重建检索 chunks；因该错误未落库的内容需补录。
