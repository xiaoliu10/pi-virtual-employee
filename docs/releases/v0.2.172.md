# v0.2.172 — Fix: slow install teardown disabled auto-update on healthy boxes

## English

### Field report

A box on v0.2.170 reported `installation failed: pre-install cleanup exceeded 10 seconds`, immediately followed by `this machine failed 2 consecutive automatic installs (across versions); auto-install stopped`. A manual repair install became the only exit, and every later auto-update would have failed the same way.

### Root cause — three defects compounding

1. **Starvation:** the teardown ran its steps sequentially with no individual bound while only the durable-host close was allowed 8s — under a single 10s ceiling. One slow step starved the rest, and the install aborted on our own cleanup.
2. **Miscounted failure:** that abort was recorded as an install failure even though NSIS never started, polluting both the per-version and machine-wide consecutive-failure counters.
3. **Double counting:** the pending-install marker written before the attempt was never cleared on abort, so startup reconciliation counted the same aborted attempt again. One attempt reached the breaker threshold of 2 — a healthy machine permanently lost automatic updates.

### Changes

- New `electron/install-cleanup.ts`: every teardown step gets its own budget, never throws, always logs its duration. Budgets: work windows 3s, durable host 8s, IM 6s, browser 5s, computer 3s, HTTP 2s.
- Outer ceiling raised 10s → 35s (above the 27s sum of step budgets, so starvation cannot return), and an overrun is now a warning instead of an install failure — the process quits immediately after teardown, and process exit releases every handle a slow step left behind.
- An aborted preparation no longer records a failure and now drops the pending marker: one attempt counts at most one failure.
- A real failed install (app came back on the old version) is still counted exactly once.

### Verification

`scripts/test-install-preflight.mjs` (4 cases): a wedged teardown still hands over to the installer; an aborted attempt records no failure and clears the pending marker; a genuine failed install still counts once; the step helper reports ok/timeout/failed with duration logging. Mutation check: reinstating the old "timeout = failure" behavior makes the suite fail. Full gate: 68 suites, typecheck, build, immutable (manifest re-pinned with a stated reason).

## 中文

### 现场

一台跑 v0.2.170 的机器报「安装失败：安装前清理超过 10 秒」，紧接着报「本机已连续 2 次自动安装失败（跨版本），已停止自动安装」。此后只能靠手动装包修复，而且装好之后下一次自动更新还会以同样方式失败。

### 根因——三个缺陷叠加

1. **饿死**：清理步骤串行执行且没有单步上限，只有 durable 关闭一步给了 8 秒，整体却只有一个 10 秒上限。一步慢就占满预算，安装被我们自己的清理动作中止。
2. **记错账**：这次中止被记成「安装失败」，而 NSIS 根本没启动，同时污染了单版本计数和机器级连续失败计数。
3. **重复记账**：尝试前写入的 pending 标记在中断时没清，下次启动校对把同一次中止又记一遍。一次尝试就到了熔断阈值 2——一台健康的机器因此永久失去自动更新。

### 变更

- 新增 `electron/install-cleanup.ts`：每个清理步骤独立预算、永不抛错、始终记录耗时。预算为工作窗口 3s、durable 内核 8s、IM 6s、浏览器 5s、computer 3s、HTTP 2s。
- 外层上限 10s → 35s（高于分步预算之和 27s，杜绝再次饿死）；超时改为记警告继续安装——清理完进程立刻退出，退出本身会释放慢步骤遗留的所有句柄。
- 中止不再记失败，并清掉 pending 标记：一次尝试最多记一次失败。
- 真实失败（装完仍是旧版本）依然精确计一次。

### 验证

`scripts/test-install-preflight.mjs` 4 条：卡死的清理仍能交棒给安装器；中止不记失败且清标记；真实失败仍计一次；分步助手区分 ok/超时/失败并记录耗时。变异验证：把旧的「超时即失败」放回去，用例必失败。全量门禁 68 套件、typecheck、build、immutable（manifest 已带理由重钉）通过。

> Immutable guardrail change (updater-breakers): a slow self-teardown must not count as an install failure — one field abort was double-counted by startup reconciliation and tripped the machine breaker, disabling auto-install on a healthy box.
