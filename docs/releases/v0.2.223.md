# v0.2.223

## English

### Worker keep-alive window — the conversation stays with the worker that did the work

A login flow died on a false promise. The worker asked the user for an SMS verification code and its turn settled; the code arrived **2 seconds later** — and three mechanisms conspired to kill the flow:

1. **The code never reached the worker.** With the worker no longer LIVE, the bare-token gate routed 「786199」 to the foreground conversation (the shape triage called it a question).
2. **The foreground fabricated an action.** Its reply claimed 「验证码已写入 spay_code.txt」 with a shell-looking card — but it made zero tool calls; the file never existed (verified on the machine), the card was a markdown code block, not an execution.
3. **The settle sweep killed the polling script** 13 seconds after the worker settled — the one process that could have continued the login.

The user ruling: workers need a keep-alive mechanism (~2 hours); the conversation must stay sticky with the worker that did the work, because losing context is the worst experience; and shape-based judgment should not decide outcomes for a live conversation.

The fix — `general.workerKeepAliveMin` (default 120, 0 disables):

- **LIVE workers**: unchanged — everything reaches them unconditionally.
- **Done within the window**: non-task messages (bare codes, questions, follow-ups) reach the worker that did the work; bare tokens travel with a bounded excerpt of the source conversation so the worker can resolve references without guessing; task-shaped requests still dispatch fresh (a new worker carries the same excerpt, so nothing is lost).
- **Beyond the window / interrupted / cancelled**: all previous gates apply unchanged.
- **The settle sweep defers**: while the window is open, background scripts the worker spawned stay alive (they are the ones waiting for the user's answer) and are swept at window expiry — cleanup remains TTL-bounded.

The shape judgment now only runs on cold conversations, where a mistake is cheap. A verification code typed seconds after a worker asks for it reaches the session that asked; nothing claims an action it did not take.

Verification: all 140 test suites pass, both typecheck projects clean; a new regression test pins the exact incident shape (code arriving seconds after settle reaches the worker, with the excerpt attached); the sweep deferral is behaviorally tested against the real bundled manager (hot → deferred, expiry → killed); the reviewer's mutation checks confirmed the pins fail when the gates are removed.

## 中文

### worker 保活窗口——对话留在干活的那个 worker 身上

一个登录流程死在假承诺上。worker 问用户要短信验证码，回合收尾；验证码 **2 秒后**到达——三个机制合谋杀死了流程：

1. **验证码没到 worker 手里。** worker 已非 LIVE，裸 token 门把「786199」弹到前台（形状判断把它当成了一句问话）。
2. **前台编造了一个动作。** 回复声称「验证码已写入 spay_code.txt」还带 shell 样式的卡片——但零工具调用；文件从未存在（机器上实证），那张卡是 markdown 代码块，不是执行结果。
3. **收尾清理杀掉了轮询脚本。** worker 收尾 13 秒后，唯一能继续登录的进程被 settle sweep 终止。

用户裁定：worker 需要保活机制（约 2 小时）；对话必须粘连在干活的 worker 身上，丢上下文的体验最差；形状判断不应该对一个活着的对话裁决结果。

修复——`general.workerKeepAliveMin`（默认 120，0 关闭）：

- **LIVE worker**：不变——一切消息无条件到达。
- **窗口内的 done worker**：非任务消息（裸码、问句、追问）到达干活的那个 worker；裸 token 附带来源会话的有界摘录，worker 解引用不再靠猜；任务型请求仍然派发新 worker（新 worker 带同样的摘录，上下文不丢）。
- **超窗 / 中断 / 已取消**：原有门全部不变。
- **收尾清理延期**：窗口开着期间，worker 拉起的后台脚本保持存活（正是它们在等用户的回答），窗口到期统一清理——清理保证仍有 TTL 上界。

形状判断由此只跑在冷会话上，而冷会话判错的代价很小。worker 要码之后几秒内敲进的验证码，会到达要码的那个会话；没有任何环节再声称自己做了没做过的事。

验证：140 个测试套件全过、双 typecheck 零错误；新增回归测试钉死事故原形（收尾几秒后到达的码进入 worker 且摘录随行）；收尾延期对真实打包的 manager 做了行为级测试（热→延期、到期→清理）；reviewer 的变异验证确认拿掉门这些测试就会挂。
