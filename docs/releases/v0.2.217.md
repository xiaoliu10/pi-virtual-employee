# v0.2.217

## English

### Long browser-automation tasks no longer die on a context-limit wall with a misleading error

A worker session that ran for six hours (416 tool calls, ~200k in-memory tokens) repeatedly hit the model's hard 204,800-token context limit, yet the user was told the *model service was temporarily unavailable* — the service was healthy. Three stacked engine defects caused this, all fixed:

- **Compaction no longer reports a fake recovery.** Recovery used to succeed as soon as compaction ran, without verifying the transcript actually fit. A "successful" compaction that left the retained recent tail over budget skipped the guaranteed hard truncation, so every retry hit the same wall (the field log showed three compactions at ~199k→210k tokens). Recovery now verifies the result against the usable-window line and falls through to outright truncation; if even that cannot fit, it fails honestly instead of pretending recovery.
- **Length-truncated empty runs are classified correctly.** When the model spends its whole output budget on reasoning and returns no answer three times, the deterministic reply now explains the transcript is too long and points at `/new`, rather than blaming a service outage.
- **Reasoning-only truncated turns no longer accumulate.** The tail cleanup used to count thinking blocks as "content", so each failed retry piled another up-to-max-tokens reasoning block onto the transcript. It now judges on visible text only and drops the un-resumable thinking-only tail.

### Progress notes now fire for short tasks (first beat at +2 min)

Field statistics (box Nova, 3 days of logs): 16 worker tasks started a progress notifier but only 3 ever pushed a note — 15 tasks ran 0.3–17 minutes against a 10-minute interval, finishing **before the first tick**. A pure `setInterval` makes the first progress note a full interval away, so most tasks narrated nothing. The broadcaster now fires a first beat 2 minutes after start (steady cadence unchanged after it; every existing gate — liveness, suppression, preflight, backoff, cap — applies unchanged). The worker wiring also passed the wrong conversation id to the side-pass summarizer, attributing watchdog liveness and thinking-level resolution to the source chat instead of the worker session; fixed. The degraded-backoff window now logs its skips (the last silent gate).

### Configurable data root with E:→D:→C: drive probing

All profile data used to live under a hard-coded `%APPDATA%\pi-virtual-employee`. The data root is now resolved at the earliest startup phase with this priority:

1. **`PI_DATA_ROOT` env var** — explicit override; relative paths, bare drive roots (`C:\`) and unwritable targets are hard errors with a blocking dialog, never silent fallbacks.
2. **`.data-root` marker** — once a root is chosen it is pinned; re-probing on every launch would silently fall back to an empty root when a drive goes offline (indistinguishable from data loss). A pinned root that is unavailable, or whose volume fingerprint no longer matches, hard-errors with a dialog and quits.
3. **Existing installs stay where they are** — the legacy appData root is detected by content (including default-profile-only machines, whose data sits directly in the root with no `profiles/` subdir) and pinned; migration to another drive is an explicit, separate operation.
4. **Fresh installs on Windows** probe fixed drives E: → D: → C: with a real write probe, then pin.

Layout is unchanged (`<root>/profiles/<name>`, workspace sibling), so existing machines see byte-identical paths and the updater's profile detection keeps working. 17 new unit tests cover the full matrix; two independent review rounds fixed a legacy-detection gap that would have orphaned default-profile-only machines on auto-update.

## 中文

### 超长浏览器自动化任务不再撞死在上下文上限，且错误提示不再误导

一个跑了 6 小时的 worker 会话（416 次工具调用、内存态约 20 万 token）反复撞到模型 204,800 token 的硬上限，但用户收到的提示却是「模型服务临时不可用」——而服务本身是健康的。三个叠加的引擎缺陷已全部修复：

- **压缩不再「假恢复」。** 过去只要压缩执行了就判定恢复成功，从不校验压缩后是否真的能装下；当保留的近期尾部本身就超限时，保证能装下的硬截断被跳过，每次重试都撞同一堵墙（现场日志显示三次「压缩成功」token 反而在 ~19.9 万→21 万）。现在恢复会按可用窗口线复核结果，不达标就落到硬截断；若连截断都无法装下，则诚实失败而非假装恢复。
- **长度截断空跑被正确分类。** 当模型把整个输出预算花在思考上、连续三次没有正文时，确定性回复现在说明是会话内容超出长度上限并指引 `/new`，而不是诿过于服务中断。
- **纯思考的截断回合不再累积。** 尾部清理过去把思考块也算作「内容」，每次失败重试都往会话里再堆一个最多占满输出预算的思考块。现在只按可见文本判空，直接丢弃不可恢复的纯思考尾部。

### 短任务也有进度汇报了（首拍 +2 分钟）

现场统计（盒子 Nova，3 天日志）：16 个 worker 任务启动了进度通知器却只推送过 3 次——15 个任务跑了 0.3~17 分钟，而间隔是 10 分钟，全部在**首个 tick 之前**就结束。纯 `setInterval` 让第一条进度汇报隔了整个间隔，多数任务全程无叙述。现在首拍在启动后 2 分钟触发（之后稳态节奏不变；既有全部门槛——存活/抑制/预检/退避/上限——照常生效）。同时修复 worker 旁路会话 ID 误传（看门狗记账与思考档位解析落到了来源会话头上），退避窗口补上跳过日志（最后一个静默门）。

### 数据根目录可配置，Windows 按 E→D→C 探测

全部 profile 数据此前硬编码在 `%APPDATA%\pi-virtual-employee`。现在数据根在启动最早期按以下优先级解析：

1. **`PI_DATA_ROOT` 环境变量**——显式覆盖；相对路径、裸盘根（`C:\`）、不可写目标都硬报错并弹阻塞对话框，绝不静默回退。
2. **`.data-root` 标记**——一旦选定即钉死；每次启动重新探测会在盘掉线时静默回退到空根（与数据丢失不可区分）。钉死根不可用或卷指纹不匹配时硬报错弹窗退出。
3. **存量机器原地不动**——按内容检测旧 appData 根（含只在根下直接存数据的 default-only 机器）并钉死；迁移到其他盘是独立显式操作。
4. **Windows 全新安装**按固定盘 E→D→C 实测可写探测后钉死。

布局不变（`<root>/profiles/<name>`、workspace 平级），存量机路径字节级一致，updater 的 profile 反推不受影响。新增 17 条单测覆盖全矩阵；两轮独立审查修掉了一个会在自动更新后孤立 default-only 用户数据的存量检测缺口。
