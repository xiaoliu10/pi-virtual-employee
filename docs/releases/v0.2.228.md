# v0.2.228

## English

### A follow-up typed while a worker is running now reaches it — via steer, not a queue behind the whole turn

Field 2026-11-12 (`dt:manager5792`): a worker was retrying its SLS query in a loop, still selecting 「今天」 as the time range. The user appended a correction to the same chat:

> 流水号里面有这笔订单的下单时间……查询的时候可以把时间设置为前后各一天

The log recorded `FOLLOW-UP → running worker` for both appended messages — but the running inference loop never saw them. `inject()` **enqueued** the follow-up behind the entire running turn, so the correction could only be delivered after the worker had already finished (or given up on) the work it was correcting. The database confirms the timing: an earlier 「前后各一天」 correction was written into the worker's history **0.7 s after** the original task settled.

The log line was the trap: `FOLLOW-UP → running worker` proves admission to a queue, not delivery into the live turn.

v0.2.228 makes `inject()` ask the engine synchronously (right after `open()`, with no await between the liveness check and queue admission) through a new `steer()` dependency, wired to `engine.steerConversation` with the same actor shape `send()` uses:

| steer result | behavior |
| --- | --- |
| `accepted` | injected at the live turn's next step boundary; **never** re-queued as a second send |
| `rejected` (owner mismatch / turn already aborting) | an explicit 「追加指令未投递：<原因>」 reply; a failed push surfaces through `onError` and is never replayed inline |
| `idle` (including a turn that settled while `open()` awaited) | the serial follow-up contract is preserved — exactly one ordinary turn |

Two supporting fixes came out of the same investigation:

- **A `done` row can still be running a dialogue turn.** Follow-up turns deliberately do not reopen the linear state machine, so row status alone under-reported liveness. `WorkerService` now tracks `runningTurns` explicitly.
- **`worker:` sessions were skipping the steer owner check.** Legacy origin inference classifies `worker:` as console, and the console path intentionally trusts the local operator — which meant a group member could steer someone else's running task. `steerConversation` now enforces the owner boundary for `worker:` conversations as well, and additionally requires `memoryConversationId` to match the running turn's source chat.

Verification follows the delivery claim, not the routing log: a **real Agent loop** test appends the date correction while the worker's tool is still in flight and asserts the correction appears in the NEXT model request's context with `sends === 1` (no duplicate execution). Separate regressions pin the settle-during-`open()` race (exactly one serial turn), the rejected-steer path (notice pushed, never replayed, push failure only reported), and the owner boundary (foreign sender and mismatched source chat both refused before touching the queue).

Gates on the merged code: **143 test suites pass**, both typecheck projects clean, immutable-kernel gate reports 16 guarded regions unchanged.

Field-verification boundary: verified against the real SDK loop in tests; not yet exercised on the deployment box, which is held for its upgrade window.

## 中文

### 任务执行中追加的话，现在真的能送到——走 steer，而不是排在整个回合后面

现场 2026-11-12（`dt:manager5792`）：worker 正在循环重试 SLS 查询，时间范围一直选「今天」。用户在同一个会话里追加了纠正：

> 流水号里面有这笔订单的下单时间……查询的时候可以把时间设置为前后各一天

两条追加消息的日志都记了 `FOLLOW-UP → running worker`——但运行中的推理循环从头到尾没看到它们。`inject()` 把追加消息**排在了整个运行回合之后**，纠正只能等 worker 把要纠正的活干完（或放弃）之后才送达。库里也印证了这个时序：更早那条「前后各一天」的纠正，是在原任务结束后 **0.7 秒**才写入 worker 历史的。

坑就在那行日志：`FOLLOW-UP → running worker` 只证明「进了队列」，不证明「送进了正在跑的那一轮」。

v0.2.228 让 `inject()` 在 `open()` 之后**同步**询问引擎（活性判断与入队之间没有 await），通过新增的 `steer()` 依赖接到 `engine.steerConversation`，actor 形状与 `send()` 完全一致：

| steer 结果 | 行为 |
| --- | --- |
| `accepted` | 在当前回合的下一个步骤边界注入；**绝不**再排成第二次 send |
| `rejected`（发起人不符 / 回合正在中断） | 明确回执「追加指令未投递：<原因>」；推送失败只经 `onError` 上报，绝不 inline 重放 |
| `idle`（含 `open()` await 期间原回合已收尾的竞态） | 保持串行 follow-up 契约——恰好一次普通回合 |

同一次排查还带出两个配套修复：

- **`done` 行也可能正在跑对话轮。** 后续对话轮刻意不重开线性状态机，所以只看行状态会漏判活性。`WorkerService` 现在显式维护 `runningTurns`。
- **`worker:` 会话此前跳过了 steer 的发起人校验。** 旧的 origin 推断把 `worker:` 归为 console，而 console 路径有意信任本地操作者——这意味着群成员可以 steer 别人正在跑的任务。`steerConversation` 现在对 `worker:` 会话同样强制 owner 边界，并额外要求 `memoryConversationId` 与运行回合的来源会话一致。

验证对准「送达」这个主张，而不是路由日志：**真实 Agent 循环**测试在 worker 的工具仍在执行时追加日期纠正，断言纠正出现在**下一次模型请求**的 context 中且 `sends === 1`（不重复执行）。另有回归分别钉住 `open()` 期间收尾的竞态（恰好一次串行回合）、拒绝路径（回执已推、绝不重放、推送失败只上报）、以及 owner 边界（陌生发起人与来源会话不符都在入队前被拒）。

合并后代码门禁：**143 套件全过**、双 typecheck 零错、不可变内核闸门报告 16 守护区未变。

现场验证边界：已在测试中对真实 SDK 循环验证；尚未在部署盒子上实跑（盒子按升级窗口裁定保持冻结）。
