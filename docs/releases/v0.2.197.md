# v0.2.197

## English

### One shared browser, many tasks — and the ownership rules actually hold

Several tasks (a background work window, a scheduled fire, an IM turn) often need the same logged-in browser. Chromium allows exactly ONE process per profile; the loser used to die with exitCode 21 ("profile in use"), the model misread that as a broken browser, ran `taskkill /IM chrome.exe`, and destroyed every other task's session. The field incident behind this release: 40+ such kills, 31 login expiries in one day.

This release makes the shared-browser path real in `BrowserService`:

- **Explicit page ownership.** Every task owns exactly one tab, tracked in a registry. A task is never handed another task's tab, and an unknown owner always opens a fresh page — never "the current tab" (the exact behavior Playwright declined to support in #42961).
- **Popups follow event-time ownership.** Bastion hosts and admin consoles live in popups (`target=_blank`). The popup is attributed to whoever owns the opener WHEN THE POPUP OPENS, not whoever created the page — after a tab switch, a popup can no longer land in the wrong task's lap.
- **Switching tabs TRANSFERS ownership.** `switch` to another task's tab drops that task's pointer (it gets a fresh page on its next action); one tab can never have two live drivers. Closing another owner's current tab is allowed but logged.
- **No duplicate-page races.** Concurrent `getPage` calls for the same owner collapse into one page; a page creation that finishes after a switch/release is discarded (and closed) instead of overriding the registry or resurrecting a released owner. Both races were reproduced on a real Chromium and are covered by deferred-`newPage()` regression tests.

### Work items carry structured provenance

A task's origin used to be sniffed out of a free-text note (`includes("聊天转派")`), which made provenance forgeable: a row inserted straight into the database with the operator's identity and the text "从聊天转派（Router）" appeared in the operator's task list, pushed progress as "autonomous task", and re-armed its own follow-up windows — all without the operator ever asking for it.

- `work_items` now has a structured `origin` column: `chat` / `manual` / `mining` / `scheduled` / `injected` / `legacy`. The structured column always wins; the note is a claim, not evidence.
- Only chat-dispatched (and scheduled/mined-approved) items keep auto-follow-up. An `injected` row runs once and is labeled 「系统注入任务」 in every push header — it can no longer impersonate a Router-dispatched task.
- Every creation path stamps the real origin: Router dispatch → `chat`, admin-ordered autonomous work and mined proposals → `mining`. The "foreground escape" hatch also resolves origin structurally, so an injected row cannot be pulled to the foreground by claiming chat dispatch in its note.
- Legacy rows (pre-column) keep their historical behavior and wording — no in-flight task is disrupted by the migration.

### Also in this release

- Widget: the "thinking" header no longer squeezes into vertical one-character-per-line stacking at narrow widths, and the default floating size was enlarged.
- Scaffolding, honestly labeled: a CDP endpoint module (race-free port discovery via `DevToolsActivePort`, stale-file detection) and a credential-snapshot module (SQLite online backup, consent-revocation cleanup) ship TESTED but not yet wired into the launch path — `BrowserService.launch()` still uses Playwright's persistent context. Wiring them in is the next PR; nothing in this release pretends otherwise.

## 中文

### 一个共享浏览器跑多个任务——而且归属规则真的守得住

后台工作窗口、定时触发、IM 会话经常要用同一个已登录的浏览器。Chromium 每个 profile 只允许一个进程，输家以前直接死于 exitCode 21（profile 被占用），模型把它误读成"浏览器坏了"，然后 `taskkill /IM chrome.exe` 把其它任务的会话全部杀掉。本版本背后的现场事故：一天 40+ 次误杀、31 次登录态丢失。

本版本把共享浏览器路径在 `BrowserService` 里做实：

- **显式页面归属。** 每个任务拥有且只拥有一个标签页，登记在注册表里。任务永远不会拿到别人的标签页；未注册的 owner 一律新开页面，绝不返回"当前页"（Playwright 在 #42961 拒绝支持的行为）。
- **弹窗按事件时刻归属。** 堡垒机、后台系统靠弹窗（`target=_blank`）工作。弹窗归属在**弹窗打开那一刻**反查开启页的 owner，而不是页面创建时的闭包——切换标签页之后，弹窗不会再落错任务。
- **切换标签页即转移所有权。** `switch` 到别的任务的标签页会立即吊销对方的指针（它下次操作拿全新页面）；一个标签页永远只有一个活着的操作者。关闭别人正在用的标签页是允许的，但会留下审计日志。
- **建页竞态清零。** 同一 owner 的并发 `getPage` 合并为一次建页；建页等待期间发生的切换/释放会让迟到的创建作废（新页直接关闭），既不会覆盖注册表，也不会把已释放的 owner"复活"。两个竞态都在真实 Chromium 上复现过，并有延迟 `newPage()` 的回归测试钉住。

### 任务带上结构化来源

任务的来源以前靠自由文本嗅探（`includes("聊天转派")`），等于谁都能伪造：一条直接写进数据库、带着管理员身份和「从聊天转派（Router）」字样的记录，出现在管理员任务列表里、按"自主任务"推送进展、还自动续期跟进——管理员从未提出、也从未同意过。

- `work_items` 新增结构化 `origin` 列：`chat` / `manual` / `mining` / `scheduled` / `injected` / `legacy`。结构化列永远优先；备注只是声明，不是证据。
- 只有聊天转派（以及定时、已批准的挖掘）任务可以自动续期。`injected` 记录只跑一次，推送标题如实标注「系统注入任务」，不再冒充 Router 转派。
- 所有创建入口都写入真实来源：Router 转派 → `chat`，管理员直接创建的自主任务与挖掘提案 → `mining`。「前台执行」逃生门同样按结构化来源判定——注入记录无法靠备注自称聊天转派而逃到前台。
- 旧数据行保持历史行为与文案，迁移不打扰任何在跑的任务。
