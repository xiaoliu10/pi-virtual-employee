# 前台会话响应延迟与后台任务吞吐（2026-11-03 调研）

> 背景：现场反馈「自主任务的脚本可以很快，聊天任务却很慢」。本文定位瓶颈、
> 对比可选架构，并给出结论。

## 一、为什么「脚本快、聊天慢」是错觉

自主任务的脚本（`run_command` 里 python）之所以「快」，是因为**用户看不到它**：
它跑 40 分钟也没有任何中间态投递，最终一次性给结果。聊天任务的每一步都在
IM 卡片上刷新，主观感受就是「慢」。

真正的差异只有两点：
1. **任务规模**：聊天回合通常是用户当轮刚描述的任务，往往真有多步；
2. **可见性**：回合任务每步都渲染，脚本只渲染最后一行。

结论：**延迟本身不是脚本/回合的机制差异，而是任务规模 + 反馈密度差异。**

## 二、实际瓶颈（按影响排序）

### 1. 前台会话承载长任务（最大）
一个 IM 会话串行跑一个回合；长任务（30-90 分钟）占住会话，群内其他人只能
排队。这就是「群里任务全部被卡」的直接机制——与执行速度无关，是**串行队列
被长任务占死**。

### 2. 后台调度串行（次要）
Scheduler 对同一 profile 的任务串行触发，但不同 profile（Nova/Synapse/Orion）
本来就并行，所以现场体感是「有的员工在动，有的不动」。

### 3. 完整结果屏障（体验）
任务完成前用户只能看到「执行中」。进度汇报（v0.2.171/173/175）部分缓解，
但**任务开始前没有任何预期**——用户不知道要等多久、会做什么。

## 三、Router / Worker 模式评估

**结论：现阶段不做。** 理由：

1. **VE 的模型调用已经是可并发的**（不同会话、不同 profile 本来就并行）；
   加一层 router 不会让单个会话的回合变快。
2. **durable 内核的设计前提是单会话串行**（submission 队列保证事务一致性），
   router 化等于重写会话模型，收益却是「多个会话并行」——而这已经有了。
3. **关键外部发现**：pass-through 不加速任务完成。让用户提前看到首字并不缩短
   端到端时间，只改变感受。真正该修的是「占死队列」和「无预期」。

## 四、采纳的两步走

### 方案 A：不阻塞前台（已部分落地）
- 进度汇报（已发）：任务执行中周期性推送四段式进展；
- **任务规划先行（本版新增）**：执行前先出一份编号规划推送回聊天，
  再开始执行——解决「无预期」，成本是一次 60 秒上限的旁路 LLM 调用。

### 方案 B：长任务后移（未做，需产品决策）
- 群里的长任务自动转为后台 work item（window），前台立即回执
  「已转后台执行，完成后通知」；
- 需要产品层确认：用户是否接受「群内指令不立即执行」。
