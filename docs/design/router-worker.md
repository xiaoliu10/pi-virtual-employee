# Router / Worker 架构（2026-11-04 决策版）

> 决策背景：用户拍板推翻 2026-11-03「现阶段不做」的结论。现场痛点成串：
> 10:21 的消息排队 5 分钟才被处理；09:42 的监控任务占住会话 40+ 分钟；重启时
> 排队中（placed）的消息悬空不执行。根因是同一个：**聊天回合同时承担「对话
> 交互」与「长任务执行」两个职责，长任务占死前台**。本文给出完整重写设计。
> 前置阅读：`superagent-response-latency.md`（瓶颈定位）。

## 一、目标（可验收）

1. **任何 IM 消息 ≤5 秒内得到有信息量的回应**——要么直接回答，要么「已接收 +
   规划 + 已转后台 + 完成会通知」，永不静默排队。
2. **前台会话永不因长任务阻塞**——后续消息即时处理，与后台任务并行。
3. **长任务有完整的生命周期反馈**——规划（执行前）、进度（执行中，10 分钟级）、
   结果（完成时）+ 恢复保障（重启不丢）。
4. **同会话上下文不断裂**——后台任务的结果与状态对来源会话可见、可引用。

## 二、现状盘点（复用，不重写已验证的件）

| 已有件 | 复用方式 |
|---|---|
| work item / window（自主任务容器） | **Worker 的执行容器**——durable ownerless 会话 + sqlite 持久化 + 重启 resume |
| 规划先行（looksLikeTask + 旁路 LLM 编号步骤） | **Router 的分诊依据**（v0.2.187，本分支修复后可用） |
| 进度通知（四段式心跳 + tailExcerpt 节选） | **Worker 的进度通道**（taskProgressMin 节奏） |
| delivery ledger（幂等投递 + uncertain 语义） | 回执/结果投递的去重保障 |
| /stop、steering、turn watchdog | 取消/插队的前台语义（保留） |
| placed 恢复盲区 | **Phase 1 后自然消解**：长任务在 work item 里，重启 resume 已有保障 |

## 三、架构

```
IM 消息
  → Router（manager 接收层增强）
     ├─ 命令/打断/steering（/stop /new 等）→ 即时路径（现状保留，永不排队）
     ├─ 快速问答（分诊：非任务/单步）→ 直接回合回答（现状）
     └─ 任务型（分诊：多步/耗时动作）
          → 立即回执（≤5s）：📋 规划卡片 + 「已转后台执行，完成后通知」
          → Worker 派发：自动建档 work item（来源会话/发起人/规划作为 prompt）
          → window 执行（现有窗口机制：预算、心跳、暂停/恢复、学习）
          → 进度心跳 → 来源会话（10 分钟级）
          → 完成推送 ✅ 结果 + 明细链接 → 来源会话
```

**Router 的职责**：接收、ACK、分诊、派发、前台保序。**Worker 的职责**：
执行、心跳、收尾、学习。两者以 work item 为唯一交接凭证（id 持久化）。

## 四、关键设计决策

### D1 分诊：谁进 Worker（保守优先）

误把简单问题转后台是最差的体验（「你好」→「已转后台」）。分诊必须保守：

- `looksLikeTask` 为 false → 前台直接回答（现状）。
- 为 true 时看**规划旁路的产物**：编号步骤 ≥2 且命中耗时动作动词
  （部署/抓取/批量/爬取/监控/导出/登录+X）→ 转 Worker。
- 单步即时动作（「现在几点」「这条数据是什么意思」）→ 前台。
- 兜底：规划旁路失败（LLM 不可用）→ 维持现状（前台执行），**分诊失败不得
  把消息变黑洞**。

### D2 Worker 容器：复用 work item，不造新引擎

work item 已有：持久化（sqlite）、窗口预算（maxMinutes）、进度心跳、暂停/
恢复、waiting_human、学习回路、结果推送、重启 resume。长任务聊天消息转成
一个 **auto-created work item**（`source: "chat-dispatch"`），全部机制免费
获得。不引入第二套执行引擎。

### D3 来源绑定与上下文

- work item 记录 `origin_conversation`（现有字段）——结果回投到来源会话。
- 后台执行用 **durable ownerless conversation**（现有 window 语义）：与前台
  会话的上下文天然隔离；结果推送带 work item id，前台会话引用它即可续问
  （「刚才那个任务」→ my_stats/work item 查询已支持）。
- 后台任务产生的**新请求**（用户在结果下追问）→ 走前台分诊：能答则答，
  需要重跑则派新 work item。

### D4 回执与预期（Router 的 ACK 语义）

回执 = 规划卡片 + 一行状态（≤5 秒内，两段消息合一）：

```
📋 任务规划：登录 spay 系统，抓取昨日账单，导出 Excel
  1. …
  2. …

🚀 已转后台执行（编号 W-123），完成后在本会话通知。
期间可随时发送「W-123 进度」查看，或 /stop 取消。
```

### D5 恢复语义

work item 持久化于 sqlite，窗口重启 resume 已有（0.2.174 语义）。Phase 1
后聊天队列里不再滞留长任务（长任务在 work item 里），**placed 盲区的实际
暴露面缩到「前台快速问答被重启打断」**——其修复（placed input 重新驱动）
作为独立小修并行落地，不依赖本架构。

### D6 与现有开关的关系

新增 `general.chatDispatch`（默认 off 首发灰度 → 验证后默认 on）：
- off：完全现状（前台执行）。
- on：分诊 + 转 Worker。
进度心跳节奏沿用 taskProgressMin（任务级 30 分钟）——转后台后这个节奏是
合理的；chat 节奏（longTaskProgressMin）只管仍在前台的回合。

## 五、分阶段实施

| 阶段 | 内容 | 发布 |
|---|---|---|
| **P1 核心闭环** | 分诊 → 自动建档 → 立即回执 → window 执行 → 结果回投；`chatDispatch` 开关；分诊保守阈值 | 0.2.189 |
| **P2 分诊精细化** | 旁路评估步骤数/预估时长；多 Worker 并发上限（同 profile 窗口数）；插队优先级 | 0.2.190 |
| **P3 恢复完善** | placed input 重新驱动（独立小修，可提前）；Worker 队列可视化（控制台） | 并行 |

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 分诊误判（简单问题转后台） | 保守阈值 + 「转后台」回执里带「回复『前台执行』可立即切回」逃生门 |
| 后台任务结果爆炸刷屏 | 结果推送复用 splitForPush + 明细走 OSS 链接（现状） |
| window 预算耗尽任务未完 | NEXT_CHECK 顺延（现状）+ 回执里写明预算 |
| 多 worker 资源争抢 | P2 并发上限（默认 2/ profile） |
| 分诊旁路 LLM 失败 | 维持现状前台执行（D1 兜底） |

## 七、验收清单（P1）

- [ ] 长任务消息 5 秒内收到规划+转后台回执
- [ ] 回执后 5 秒内同会话再发消息，前台即时响应（不被阻塞）
- [ ] 后台任务进度按 taskProgressMin 推送
- [ ] 完成推送带结果与来源会话一致
- [ ] 重启后 window resume，任务继续且来源会话收到恢复通知
- [ ] `chatDispatch=off` 时行为与现状逐字节一致
